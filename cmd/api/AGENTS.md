# cmd/api — Agent Navigation

Process entry point: configuration, wiring, lifecycle, expired-session cleanup, embedded frontend serving.

## Open this file when

- changing startup/shutdown, signal handling, or dependency wiring;
- touching the database open path, the expired-session cleanup task, or frontend serving.

## Folder-local conventions

- Serving opens via `database.OpenApplication` ONLY — never run migrations here (docs/patterns/go/sqlite.md; `cmd/migrate` is the explicit step). The opener also refuses while a `restore.marker` exists (docs/patterns/go/sqlite.md rule 12) — a staged restore in progress (or a crashed one) fails startup closed, and the `/health/ready` checker reports not_ready through the same gate.
- The expired-session cleanup wiring lives in `cleanup.go`: bounded batches, startup pass, hourly ticker on the signal context, WaitGroup-joined before DB close.
- The media orphan sweep wiring also lives in `cleanup.go`: `sweepMediaOrphans` + `startMediaSweep` — startup pass + hourly ticker on the same signal context and WaitGroup; the policy lives in `internal/media.Sweep` + `store.ReferencedMediaPaths`, never inline.
- The audit-retention cleanup wiring is the third sibling (all three in `cleanup.go`): `cleanupAuditEvents` + `startAuditCleanup` — startup pass + hourly ticker, 365-day window (`auditRetentionWindow`), bounded batches via `store.DeleteExpiredAuditEvents`; failures are logged and retried on the next tick (hygiene, not correctness).
- The WAL-size monitor is the fourth sibling: `checkWALSize` + `startWALMonitor` read the main file and `-wal` sidecar sizes (`database.FileName`) and log one line hourly — Warn at `walWarnBytes` (64 MiB, ~16× the default auto-checkpoint). It never checkpoints or tunes (docs/patterns/go/sqlite.md rule 13); a large reading is a high-water mark, not proof of growth. It takes no database handle, so it lives beside the others without participating in the DB close ordering.
- The four siblings are DELIBERATE verbatim copies: the startup passes stay explicit in `main.go` (each with its own budget and failure message) and the shapes differ enough (int64 count vs `media.SweepStats` vs a dataDir param vs a pure filesystem read) that a shared periodic-task helper would add an abstraction for no clarity. A helper would not remove the task-specific signatures, startup budgets, or logging, so the four stay separate.
- Periodic tasks start only after every fail-closed startup check (SMTP/VAPID wiring included), so an error exit never leaves a task running; on the graceful path `main` waits for them via `cleanupWG`, then closes the pool explicitly and logs a close error (the `os.Exit` branches run no defers — the deferred close never executes there; the graceful path's explicit close is what reports an error). A fatal server error cancels the signal context and falls through the same orderly shutdown before exiting 1.
- The durable audit writer is registered here right after the DB opens: `audit.SetWriter(&store.AuditWriter{DB: db})` — once at startup, before serving. The two audit-wiring tests in `main_test.go` are SERIAL (they register the package-global writer and restore nil on cleanup).
- Dev has only `web/dist/.gitkeep`, no build: HTML requests get 503 and startup logs "embedded index.html read failed" AND "embedded sw.js read failed" (both reads fail — expected during `go run`). (The "frontend not embedded" branch fires only when the dist directory is absent from the embed entirely.)
- PWA serving: `/manifest.json`, `/sw.js`, and `/icons/*` are special-cased to `no-cache` BEFORE the immutable hashed-asset branch; `sw.js` also receives the serve-time version injection (`SF_VERSION = "dev"` placeholder → deployed version, the `app-version` meta mechanism). `newFrontendHandler(fsys, version)` is the testable seam (`fstest.MapFS` tests in `frontend_test.go`); `frontendHandler` wraps it with the embedded FS + the 503 fallback.
- Frontend serving contract (`frontend.go`): a file found under the dist root is served with `Cache-Control: public, max-age=31536000, immutable` (the PWA paths above stay `no-cache`), and `index.html` is served for `/` and `index.html` only. Any OTHER unmatched path falls back to the processed `index.html` with the security headers and `Cache-Control: no-cache` (the shell always revalidates, so a deploy's new asset hashes are seen at once) — EXCEPT a missing `/assets/*` file, which answers 404: the fallback serves routes, not a broken deployment. Unknown `/api/v1` paths never reach this handler: the namespaces answer JSON 404s.
- `testutil_test.go` holds the main-package lifecycle fixtures (`openMainTestDB`, migrated temp DB); `main_test.go` holds the tests.
- `secure` / trusted-origin values are config-driven from here (`cfg.AppEnv == config.EnvProduction` + `cfg.TrustedOrigin` — `APP_ENV`/`TRUSTED_ORIGIN`). Client identity comes from `middleware.ClientAddr` (the left-most `X-Forwarded-For`); the trust boundary is Caddy's `trusted_proxies` + `trusted_proxies_strict`, and the app deliberately carries no allowlist of its own (see `internal/middleware/AGENTS.md`).
- The log sink wiring lives in `logging.go`, beside main, so the dual-sink contract is testable: `fileSinkHandler(dataDir, stderrHandler)` returns the multi-handler (stderr plus the file sink) plus a close function, and NEVER fails startup — a sink that cannot be opened returns the stderr handler unchanged with an error the caller only warns about. `logHandlerOptions` is the single level switch both sinks share (Info). main attaches it AFTER the data directory exists and BEFORE any request is served, so `middleware.RequestID` scopes the final default logger (`slog.Default()`) for every request. The sink path is `<dataDir>/logs/app.log` + `.1`–`.3`; the writer's failures report to stderr directly (`reportLogSinkFailure`), never back through slog, which would loop the logger into itself.
