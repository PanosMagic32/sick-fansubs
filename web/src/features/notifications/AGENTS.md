# web/src/features/notifications — Agent Navigation

Notifications feed: the data-access modules, the `/notifications` page, the push settings, and the badge-refresh event the header listens for.

## Open this file when

- changing the feed's wire calls, the page's states/guard/mark-read behavior, the push settings, or the catalog copy (`el.notifications` group lives in `shared/catalog/el.ts`).

## Folder-local conventions

- Every list item carries the viewer's `read` flag: unread rows carry the accent bar + tint and the full text token, while read rows keep the base muted text — the state is never a contrast reduction (`opacity` on the row would push normal text under 4.5:1). The badge rides `unread-count`; an unread row also renders a visually hidden «Αδιάβαστη» indicator (`el.notifications.unreadRow`) so its state reaches assistive tech. `read` is what makes the delete controls composable, so it is load-bearing on the wire: never remove it to save a field.
- Deletion covers every row. One at a time: `DELETE /notifications/{id}` — an event row is deleted; a visible ledger (account) row is DISMISSED for the viewer (the audit record survives) — and the masked 404 covers unknown, foreign, invisible, and already-dismissed ids, so a repeat delete is a 404 too. Bulk: `POST /notifications/clear-read` removes every READ event row (unread rows survive; ledger rows stay) and `POST /notifications/delete-all` empties the whole feed behind a `window.confirm` (event rows deleted, visible ledger rows dismissed). Both bulk verbs are idempotent 204 server-side; the per-item delete is single-shot — a repeat is the masked 404. The per-item control is an ICON button (`icons.trash`) on EVERY row: `aria-label` + `title` carry `el.notifications.deleteOne`, swapping to `deleteOnePending` while the request is out. In-flight controls use `aria-disabled` (not `disabled`) so focus survives the request; the handler's id latch refuses a second press. The page-level toolbar verbs (`markAll`, `clearRead`, `deleteAll` — the last the danger variant) keep their TEXT, and `markAll` renders only while an unread row exists.
- **The per-item control sits INSIDE its card.** The delete button is absolutely positioned in the entry's top-right corner (every row carries `has-delete`, which the entry's `padding-right` reservation hangs off); on the phone band the header STACKS — title on its own line, verbs below (`flex-wrap: wrap` at base, a column at ≤700px). The header keeps ONE title style in every state: left-aligned whether the feed is loading, empty, or populated.
- The paging controller runs with `syncOnConnect: false`: the `updated()` authenticated latch owns the first load. With the default connect sync the page would issue TWO list requests per mount — one before the session was known (a 401 risk), aborted by the latch's request. Pinned by "exactly ONE list fetch per authenticated mount".
- **Awaited item flows are generation-guarded.** `_listGeneration` bumps on every successful load, on delete-all, on a confirmed per-row delete, and on a local removal that changes the list; the items section captures it before an await and skips its local mutation and navigation when the list was replaced or the page torn down (the badge event still fires — the server-side change stands). The toolbar has ONE pending gate (`_bulkPending`): while any bulk verb runs, all three are `aria-disabled`, so mark-all, clear-read, and delete-all can never overlap; a bulk response that races a newer load re-syncs instead of filtering a list it does not own. An unknown wire kind is filtered out at load (with a console warning) and never rendered through the account template — the same refusal the unknown-draft-action branch and the service worker make.
- **Local removals move the pager facts.** `_removeItem` and clear-read decrement `total`; when the page empties while `hasNext` is true, the page advances to the cursor (or back on a last page) instead of rendering the empty state over an unreachable feed. The pager stays mounted while a page turn loads (`aria-busy`; the arrow controls use `aria-disabled`, and the size select is natively disabled with focus restored), so the pressed Next/Previous control keeps focus; it is hidden when the page has no rows and on a load error (the error banner owns that state). Bulk and per-row actions announce their outcome in the persistent `.notifications-announcer` live region, and a successful delete — or a clear-read that withdraws the last read-row control — hands focus to the feed heading.
- The page guard is the AUTHENTICATED floor: anonymous → `/sign-in`; there is NO role gate — non-staff viewers simply get no account items (the server role-weights the audit half).
- The wire items are the per-kind DTOs under one envelope — the discriminated union in `data-access/types.ts` mirrors the Go per-kind DTOs and the OpenAPI `NotificationItem` oneOf exactly (`kind` IS the discriminator; account items carry the event name as `kind`). `data-access/notifications-api.ts` owns the request functions and the kind guards.
- Account items: mark-read with NO navigation; `comment_reply` AND `heart` items: mark-read + navigate to `/blog/{contentId}#comment-{commentId}` (or `/projects/…`) — the thread's focus contract. `comment_removed` marks read + navigates to the content page with NO fragment (the comment is gone). The navigation is skipped when the mark-read's 401 kicked off the guard's `/sign-in` redirect.
- The heart item line is the heart sentence form: `verbHeartOpen` + content title + `verbHeartClose` + actor — "Το σχόλιό σου στο {title} αρέσει σε {actor}". The "σε" + bare username keeps it gender-free (no στον/στην agreement — the catalog rule). The heart item shares the comment field set; the `isComment`/`isHeart` guards stay separate because the line composition differs.
- `CommentNotificationItem` covers BOTH `comment_reply` and `comment` (same wire shape — the verbs differ: `verbCommentReply` for replies, `verbComment` for top-level comments); `ContentUpdatedNotificationItem` has NO `commentId` (the content is the navigation target — `_contentURL`, no fragment). Guards: `isComment`/`isHeart`/`isContentUpdated`/`isNewContent`/`isCommentRemoved`/`isDraftActivity`. The push-kind labels (`pushKindComment`/`pushKindUpdated`) map through `_kindLabel` in `ui/push-preferences-section.ts`.
- `new_content` reuses the content_updated wire shape (no `commentId`) — the kind is the only discriminator; `_contentItemTemplate` renders BOTH content-level kinds with the per-kind verb (`verbContentUpdated` / `verbNewContent` «δημοσίευσε το»), and `_onItemClick` navigates both to the content page.
- `comment_removed`: the line is the ACTORLESS sentence `verbCommentRemovedOpen` + title + `verbCommentRemovedClose` (no actor element, `actorUsername` always null — the moderator is never named). Its click navigates to the CONTENT page with NO fragment. The push kind joins `PushNotificationKind` (label `pushKindRemoved`); the worker composes the same sentence and skips the fragment for it.
- `draft_activity` (staff-only): the `draftAction` field (`created`/`updated`/`unpublished`) picks the verb; the line is the `content_updated` shape (actor + verb + title, no `commentId`). Its click navigates to the STAFF editor (`/admin/blog/{id}` / `/admin/projects/{id}` — `_staffEditorURL`, NOT `_contentURL`: the content is unpublished). The worker composes the same sentence and the same staff-editor deep link; both are pinned by `core/push-artifacts.test.ts`. An unknown `draftAction` renders NO item and raises NO notification — never a wordless or wrong-verb line. The preference kind joins `PushNotificationKind` (label `pushKindDraft`); the server withholds it below moderator, so the settings section renders whatever the list returns and role-checks nothing.
- A null `actorUsername` renders `el.notifications.systemActor` (the maintenance pseudo-actor or a deleted actor), EXCEPT on `comment_removed` items, whose null actor is by design and renders no actor element at all (`_commentRemovedItemTemplate`); a null `targetUsername` renders `el.notifications.missingTarget`; a null `contentTitle` renders `el.notifications.genericContent` (deleted or no longer published content), and for `comment_removed` a null title falls back the same way.
- The per-event verbs are catalog copy phrased around the masculine noun «ο χρήστης» so no gendered agreement is needed (see the catalog comment). The target's role chip maps through the shared `roleLabel` helper (`shared/utils/roles.ts` — the account/admin/notifications rule-of-three) — never new role copy.
- `NOTIFICATIONS_CHANGED_EVENT` is exported from `notifications-page.ts` and imported by `core/shell/app-header.ts` — the page owns the event name (the `NAVIGATE_EVENT` precedent). The per-kind item templates, the verbs, and the per-item read/delete flows live in `ui/notification-items-section.ts` as a reactive section controller rendered through `template()` (components.md rule 16).
- **Self-test send:** the settings section's `.push-test` button (visible only inside the subscribed branch) presses the channel for real: `sendTestPush()` → the server → the push service → this device. The result line is composed by `_testResultLine()` in `ui/push-subscriptions-section.ts` from THIS device's own row in the response's `endpoints` list, in five branches: accepted → `pushTestSent` (the SERVER-side outcome — the copy deliberately does not promise that a notification appeared), refused → `pushTestDeviceRejected`, no response at all (the row carries no `status`) → `pushTestDeviceUnreachable`, removed by the dead-endpoint rule → `pushTestDeviceRemoved`, and no row of its own named anywhere → `delivered > 0 ? pushTestSent : pushTestNone`. The user-facing lines carry no status codes, no service names and no endpoints — that detail lives in `/admin/logs` and the API response. The live region sits OUTSIDE the subscribe branch (`.push-test-result`): a removal flips the section back to the enable flow, and the sentence explaining it must survive that switch. EVERY press re-reads the row (`_refreshRowsAfterTest()`), not just a zero, so a deleted row stops rendering as subscribed. `_testPending` gates BOTH buttons — an in-flight test must not race the off switch. Wire failures go through `mapError` like every other press; the notification the worker renders is pinned in `core` (`push-artifacts.test.ts`).
- Web push: `data-access/push-api.ts` owns the seven wire functions (subscriptions list/create/delete/rename — writes `needsCSRF`; preferences get/put — the PUT body is `{pushEnabled}`; and the self-test send `sendTestPush()` — POST with no body, `200 {delivered, endpoints}` where each endpoint is `{id, service, accepted, status?, removed?}` — a COARSE push-service family and the caller's own row id, never the endpoint URL or the keys). A row's `label` is the device name: the classifier capture at subscribe time or the user's rename, null when the subscribe request's User-Agent was not recognized (rendered `pushDeviceUnknown`). `ui/push-settings.ts` is the account-page settings element (the account page hosts it — the recorded cross-feature capability edge, components.md rule 2): its state and handling live in three reactive section controllers under `ui/` (components.md rule 16). `push-subscriptions-section.ts` owns the subscription lifecycle: the double-permission flow (OUR confirm dialog first — a hasty denial PERMANENTLY blocks the origin — then the browser prompt; the confirm surface is the NATIVE `<dialog>` — components.md rule 10 — with an `open`-attribute fallback for a DOM without the method), the denied state's browser-settings hint, the off switch (DELETE the row + local `unsubscribe()` + clear the owner marker), the iOS installed-PWA hint, and the self-test. The global `<push-lifecycle>` owns the worker relay and the background heal (below); this section follows its `sf-push-reconciled` event to replace a stale local row. `push-preferences-section.ts` owns the per-kind toggles and their save fan-out (the `*bool`-backed server contract — the client never sends an absent `pushEnabled`; nothing is written until «Αποθήκευση», and only the differing kinds are PUT). VISIBILITY: the section renders NOTHING for anonymous sessions (and nothing while the session initializes), and STATES THE UNAVAILABLE LINE (`pushUnavailable`) for an environment that cannot push — an unsupported browser, or no service-worker registration (dev included — the SW registers production-only; `serviceWorker.ready` would hang the flow); the device list still renders there (managing the server's rows needs no local subscription), and a partial load failure keeps whatever arrived — the error branch renders the list beside the retry. The subscribe POST destructures `toJSON()` (`endpoint`/`keys` only — the browser's `expirationTime` must never reach the strict-JSON endpoint; pinned by the test stub's browser-faithful shape). API failures map through `mapError`; `pushFailure` is reserved for the permission refusal (a user choice, not a wire problem). The `VAPID_PUBLIC_KEY` constant lives in `@shared/config/vapid.js` — the production pair's public half, pinned equal to the Go config default, `.env.example`, and the compose fallback by the backend pin tests. The component's tests stub `serviceWorker`/`PushManager`/`Notification` per test and restore them in afterEach (the shared-window leak rule, testing.md). The iOS detection and the installed check come from `@shared/utils/platform.ts` (`isIOS`/`isStandalone`), and the hint condition reads `isIOS() && !isStandalone()` — the display-mode term suppresses the hint once the app is already installed.

- **Device list:** `ui/push-devices-section.ts` is the third section controller — the caller's rows with the name (the classifier capture or the user's rename, `pushDeviceUnknown` on null), the registration instant, the `pushDeviceCurrent` badge, and the icon actions (rename on EVERY row; delete only off the current row — the off switch owns that one, and a remote delete needs no local cleanup: that device simply stops receiving until push is enabled there again). One list fetch per mount: the subscriptions section's load hands the rows over (`applyLoaded`), and the flows that change server rows ask the section to re-read — after a subscribe, a disable, and every self-test press (`_refreshRowsAfterTest` always re-reads the list and feeds the rows, so a dead row the send removed disappears from every section); a fresh hand-over supersedes any re-read still in flight (and a fresh load supersedes a test press's re-read), and reads and writes carry separate abort controllers, so a superseding read can never cancel a delete or rename. The rename field clamps drafts to the server's rune bound (`MAX_DEVICE_NAME_RUNES`, pinned equal to `maxPushLabelRunes` by the backend pin test). Rename is a native `<dialog>` (the subscribe confirm's pattern) holding a `<form>` with the input: an empty trimmed name is refused client-side (`pushDeviceRenameRequired`, no request), the server's 422/404 maps through `mapError` into the dialog, and success patches the row label locally (the PATCH body is `{label}`, trimmed). The current row's delete is absent from the markup AND re-checked in the section's click handler, so a stale re-render cannot fire it against the live local subscription. The two dialogs share one shadow root, so each section queries its OWN class (`dialog.push-subscribe-dialog` / `dialog.push-device-dialog`) — a bare `querySelector("dialog")` would pick whichever renders first once the device list exists.

### Global push lifecycle

- **`data-access/push-subscription.ts` owns the per-device marker and the
  subscribe/reconcile helpers.** `sf-push-owner` stores the account id that
  explicitly enabled push on this browser. It is written by an explicit
  subscribe and cleared by an explicit unsubscribe, by dismissing the
  recovery prompt, or by sign-out (which also releases the row and the local
  subscription). `subscribePush` is the one subscribe path (the account
  section and the global prompt both call it), and it sends the opt-in
  `{endpoint, keys, takeover: true}` body — the only shipped path that sets
  the flag, which lets the server claim an endpoint another account owns.
  It never writes the marker itself: each caller records the owner only
  after re-checking that the live session still names the account that
  started the flow, so a switch during the permission prompt leaves no
  stale marker behind.
- **`<push-lifecycle>` is mounted once in `app-shell`.** It consumes the
  session context and runs `reconcilePushSubscription(userID)` on the first
  authenticated state, on `online`, on a visible `visibilitychange`, and on
  the worker's `sf-push-subscription-change` message. Concurrent triggers
  collapse into one in-flight run plus one queued follow-up.
- **The marker gates the client; the server is the hard boundary.**
  `UpsertPushSubscription` reassigns a foreign endpoint, so a shared browser
  must never heal a subscription for an account that did not opt in on it.
  Reconcile heals only when the marker names the current user, and its heal
  POST omits `takeover`: `UpsertPushSubscriptionNoTakeover` refuses a foreign
  endpoint with 409, and the client then clears the stale marker and reports
  `not-owner` instead of retrying. A missing marker is adopted only when the
  user's server rows already contain this browser's endpoint — that pairing
  proves a pre-marker subscriber opted in on this device. A marker naming
  another account is never overwritten.
- **An existing local subscription is healed, a missing one is prompted.**
  When the browser has a subscription whose endpoint is absent from the
  user's rows, reconcile POSTs it back. When the browser has no subscription
  while the marker matches, the element never calls `subscribe`: it shows a
  slim prompt under the header with an explicit enable control. The enable
  press requests permission, re-checks the session, calls `subscribePush`,
  records the marker, and announces the new row through
  `sf-push-reconciled`. The visible prompt copy is `aria-hidden`; the
  persistent status region carries the single accessible copy (the
  `<pager-status>` precedent), so a virtual cursor does not hear it twice. A
  denied permission suppresses the prompt but still announces `pushDenied`
  in that region, with the browser-settings hint; dismissing the prompt
  clears the marker so later boots do not ask again.
- **The global lifecycle owns the relay; the account settings section
  listens for `sf-push-reconciled`** and replaces its local row, so an off
  switch can never DELETE a row the browser no longer uses. The worker wraps its
  `clients.matchAll` relay in `event.waitUntil`, and the page still owns the
  authenticated POST (the worker has no CSRF context).
- **Sign-out releases this browser's ownership.** `releasePushOwnership()`
  runs before the session ends: it deletes the matching server row, calls the
  local `unsubscribe()`, and clears the marker. Cleanup is best-effort, but
  the marker is cleared even on failure, so a shared browser never hands the
  previous account's notifications to the next one.
- **The prompt's live region is persistent.** The host renders an empty
  `role="status"` element from the first paint and fills it after the async
  reconcile; the visible prompt is a labelled region (`pushTitle`). While
  healthy the host is `display: contents`, so the live region takes no layout
  space and no strip margin remains.
- Deploy itself does not rotate subscriptions; this covers browser/OS
  rotation, permission changes, and storage loss.
