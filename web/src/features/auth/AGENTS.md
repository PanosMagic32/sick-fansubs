# web/src/features/auth — Agent Navigation

Authentication feature: session provider and state machine (`data-access/`), the sign-in/register/account pages at the feature root, and the auth form chrome plus the session-bound toggles in `ui/`.

## Open this file when

- changing session lifecycle, state transitions, or auth API call sites.
- changing an auth page, the form directive, or the page-local guard.

## Placement

- Features are isolated constructs: auth-related code lives here only; the code splits into `data-access/` and `ui/`. The route targets (sign-in, register, forgot, reset, verify, account) sit at the feature ROOT with their `.css`/`.test.ts` beside them; `ui/` keeps the children and sheets that are not route targets — `form.css` (the auth card/form chrome), `submit-errors.ts`, the session-bound `favorite-toggle`/`follow-toggle`, and the account page's section controllers (`account-{profile,favorites,sessions,security}-section.ts`) (`form-field` graduated out to `shared/ui/`).
- Features never import other features except the recorded capability edges (components.md rule 2;
  `architecture.test.ts` guards the list): the blog/project detail pages import `ui/favorite-toggle.js`
  and `ui/follow-toggle.js` from here, and the account page imports the notifications feature's
  `<push-settings>`. Cross-feature UI primitives otherwise graduate to `shared/ui/`; the HTTP
  transport stays in `shared/api/`.
- `submit-errors.ts` stays in `ui/` deliberately: `focusFirstInvalid` queries and focuses the DOM, so it is not pure `utils/` material.

## Folder-local conventions

- `@consume` must pass `subscribe: true` — one-shot delivery otherwise strands pages mounted before bootstrap settles on the loading spinner (regression-tested).
- Context fields carry the `@consume`/`@provide` decorator alone — the decorators trigger updates themselves.
- The `sessionContext` Symbol default is the context's IDENTITY (this @lit/context version matches providers/consumers by reference to the truthy default) — do not change it to `undefined` or `{}`; consumer fields are honestly `session?` because unprovided consumers never receive the default.
- Submit errors go through the shared `ui/submit-errors.ts` (`mapSubmitError` + `focusFirstInvalid`) — a new form passes its `serverField` predicate and page-specific hooks instead of copying `_mapSubmitError`.
- 429 windows: `mapSubmitError` returns `retryAfterSeconds`; pages mount the shared `RetryCooldownController` (in `submit-errors.ts`) which owns the ticking + disconnect cancel, and keep the submit disabled for the whole window with the ticking seconds as the BUTTON label. The banner stays static on purpose — `error-banner` is `role="alert"`, and per-second message changes would re-announce the alert every second. Submit handlers must also guard `_cooldown.left > 0` — implicit submission (Enter) bypasses the disabled button. The pure `startRetryCountdown` ticker stays beside its only consumer — moving it to `utils/` would be ceremonial.
- `revalidate()`'s in-flight `_revalidating` dedupe guard is the accepted design — pinned by the focus-storm test in `session.test.ts`; do not remove the guard.
- The account-page guard stays page-local deliberately: its two page-specific exceptions (`pending`, `_passwordChanged`) would force a shared controller to parameterize for a single consumer.
- Pages `revalidate()` after any changePassword 401/403/network failure and after a sign-out/sign-out-all 403 — the 401 is ambiguous (wrong password vs dead session), the 403 means a stale in-memory CSRF token — the revalidate heals a genuinely revoked session.
- Registration sends `{username, email, password}` only — `confirmPassword` stays client-side (the Go handler rejects unknown fields). Register field errors name the failed rule per field+code: `register-page.ts` passes `registerViolationMessage` as the shared mapper's `violation` hook (username length/charset/taken, email format/taken, password min/max → dedicated `el.auth.register*` copy), and an unmapped pair keeps the generic `violationMessage` fallback — raw codes and server text never reach the UI.
- The `_disconnected` latch resets in `connectedCallback` — a removed-and-re-added provider must revalidate again; do not remove the reset.
- `data-access/types.ts` mirrors the Go auth handlers — update both sides together when a wire shape changes.
- Profile: `data-access/profile-api.ts` carries the profile endpoints — GET /api/v1/users/me (built on the shared transport; no CSRF, no 401 suppression — a profile 401 is a genuinely dead session and the global transition stays active), `changeEmail` (PUT /users/me/email), and `uploadAvatar` (PUT /api/v1/users/me/avatar — multipart via `requestForm` with `method: "PUT"`, CSRF attached, returns the refreshed profile). The `UserProfile` wire type lives in `types.ts` mirroring the Go `handler.UserProfile` DTO; `avatarUrl` is the ABSOLUTE served URL (server-projected) — render it directly as an `<img src>`, never re-map it client-side. `changeEmail` defaults to the auth-action deadline like the auth-api endpoints. The account page owns the profile load: page-owned AbortController composed via `requestSignal`, the `_profileFetched` latch stops the `updated()` hook from refetching when `revalidate()` re-sets the session state object, and the retry button calls `_loadProfile()` directly. That latch and the load live in `ui/account-profile-section.ts` (`hostUpdated()` reading the page's `authed` accessor), and the avatar widget lives with them; its widget shape: pick → local object-URL preview (`_avatarLocalURL`, revoked on replace/teardown — the media-upload widget contract) → one-step upload; confirmed updates only (a failed upload keeps the confirmed avatar; the LOCAL preview stays visible while the pick awaits retry); 413/422 map to `el.account.avatarTooLarge/avatarInvalid`; a CONFIRMED success dispatches `AVATAR_CHANGED_EVENT` (`@shared/events.js`) for the header chip and moves focus to the `role="status"` success note. A server 422 on the email change focuses the first invalid field after the inputs re-enable.
- Favorites: `data-access/favorites-api.ts` (list/status/add/remove — GETs no CSRF, PUT/DELETE `needsCSRF`, all idempotent server-side) + the `FavoriteItem`/`FavoriteStatus`/`FavoriteKind` wire types. `ui/favorite-toggle.ts` is the detail-page heart (self-contained: session-gated, status load with a `_loadedKey` latch, confirmed updates, inline Greek error, 403 → silent `revalidate`). The toggle rides the shared `ToggleDebouncer` (`@shared/utils/toggle-debouncer.js`, 300 ms trailing — the same mechanism as the thread hearts; a click-play burst delivers at most one request, an even-click burst none; the button stays enabled during the window with `aria-busy` + the `.is-pending` dim and disables only during the request phase; a sign-out inside the window cancels it; the test file stubs `setTimeout`/`clearTimeout` for the debounce delay and expires windows with `timers.fireAll()`). The heart states are the shared SVG pair (`icons.heart`/`icons.heartFilled`) — one path, one box, so the glyph cannot change size when it flips — and a CONFIRMED success dispatches `FAVORITE_CHANGED_EVENT` from `@shared/events.js` (detail `{kind, contentId, favorited}`) for the detail pages' live public count. The account page owns the favorites section in `ui/account-favorites-section.ts` — the tab (`posts`/`projects`) + `after`/`limit` ride the URL via the shared `UrlCursorPagingController`; the `_favInFlight` key dedupe stops the double sync (hostConnected + the auth latch) from aborting-and-refetching the identical page; removal reloads the current page (the paging controller's `sync()`) instead of splicing; each favorite is a `<content-card shape="row" dense>` whose `overlay` slot hosts the remove control, and the card renders the indicator stats from the counts the page passes and the inline subtitle from the item (blog posts; empty for projects). The card's remove control is an ICON button (`icons.x`): `aria-label` AND `title` carry the same `el.favorites.removeAria` the detail-page toggle uses for "remove", so the two affordances cannot drift; the card's `overlay` slot places it in the row's corner and reserves the text room. **Cross-feature capability:** this import edge is recorded in components.md rule 2 and guarded by `architecture.test.ts`; a new edge is added there, not folded in silently.
- Account-section tabs: the account page's sections are internal-state tabs — Προφίλ (identity + email), Αγαπημένα (favorites), Ειδοποιήσεις (push) (the install control + `<push-settings>`), Συσκευές (the session list + the sign-out actions), Ασφάλεια (password form). **The split:** the page keeps ONE shadow root (the panels' `aria-labelledby`/`role="tabpanel"` contract and the stylesheet require it) and composes the tab strip + the panel wrappers; each panel's state, handlers, and templates live in a reactive section controller under `ui/` that renders through `template()` — `account-profile-section.ts` (profile load, verify/resend, avatar, email change), `account-favorites-section.ts` (the pager), `account-sessions-section.ts` (the list + the sign-out actions), `account-security-section.ts` (the password form + the `markPasswordChanged()` handoff). The page owns the accessors the sections share — `authed`, `sessionContext`, `pending`/`actionError`, and the constructor options (the favorites section's `isActive` gate). `role=tablist/tab/tabpanel` semantics with the APG Tabs keyboard contract (components.md rule 14: roving tabindex so the tablist is ONE tab stop, Left/Right with wraparound plus Home/End, activation follows focus); the PANELS mount on activation (exactly one is in the DOM), so the tabs carry no `aria-controls` — its IDREF would dangle (components.md rule 14) — and the association travels through the panel's `aria-labelledby` and the focus move onto it. `_onTabSwitch` clears the shared `_error` banner (an error belongs to its producing panel). The favorites load is GATED on the favorites tab (the pager's mount-time sync skips while another tab is active; switching TO favorites calls the favorites section's `sync()`), and the initial tab derives from the URL — a `?tab=` deep link opens on favorites. **The sign-out buttons live INSIDE the Συσκευές panel** (they act on the sessions listed above them) and the sign-out error banner renders in that panel. The notifications tab label is the catalog pair `${el.account.notificationsTab} (${el.account.notificationsTabPush})`, the anglicism inside `lang="en"`. **Phone band:** `.account-tabs` scrolls sideways (`overflow-x: auto` + `flex: 0 0 auto` on the tabs) and the page root carries `min-width: 0` — without it the row's min-content width propagated up through `main`'s flex item and widened the whole page. At ≤700px the profile STACKS (avatar block above the facts), the card's padding and the favorites thumbnail shrink, and the favorites remove control sits INSIDE the card (the absolute top-right corner, with the body reserving 2.5rem); at ≤560px each fact row stacks label-over-value and the `dt` min-width goes, and at ≤480px a favorites card stacks image-over-text like the search result card (`dd`'s `overflow-wrap: anywhere` would otherwise break words letter by letter).
- `AUTH_ACTION_TIMEOUT_MS` (15s, `data-access/auth-api.ts`) is the auth-action client timeout, under the server's 30s WriteTimeout — the endpoints apply it unless a caller passes its own signal (bootstrap is the exception). A timeout surfaces as a `RequestTimeoutError` that the shared submit-error mapper turns into the generic banner.
- Forced change: the authenticated session state carries `mustChangePassword` (the sign-in/bootstrap flag). Routing is proactive in TWO places — the sign-in page's guard redirects flagged sessions to `/account` instead of `/`, and the app-shell watches the session context and routes there once (a `_forcedRedirected` latch survives revalidate's state re-sets; it resets on anonymous). The account page shows `el.auth.forcedChangeNotice` while the flag is set. The server-side gate is the enforcement — these are UX routes only.
- Self-service reset: `forgot-page.ts` (identifier form, ALWAYS the generic success copy — the page never learns whether an email went out; on success focus moves to the `role="status"` note) and `reset-page.ts` (reads `?token=` ONCE in connectedCallback, removes the token from the query via `history.replaceState` immediately — other params survive; refresh/back must not replay a consumed link; NO auth guard and NO forced-change redirect — the shell exempts `/auth/reset`; `needsCSRF` attaches the token only when a session exists; a server 422 focuses the first invalid field). Success: `RESET_SUCCESS_STORAGE_KEY` in sessionStorage + `revalidate()` + redirect — the sign-in page consumes the key ONCE (read + remove) and renders `el.auth.resetSuccess`. Both pages call `auth-api.ts` directly (the profile-api precedent), not through the session context. Page tests for the fetch paths need a `waitFor` poll — the async submit handler outlives `updateComplete` (the helper is shared at `@shared/api/test-utils.ts`); the reset-page tests use the shared history-location shim (`shimHistoryLocationSync`/`restoreHistoryLocationSync` + `setHappyDOMURL`/`resetHappyDOMURL` — the token read AND the token strip both depend on the real location updating).
- Email verification + change: `verify-page.ts` — the reset-page token shape: reads `?token=` ONCE + strips it via replaceState, then auto-submits once the session context has SETTLED (the link IS the action; a session-bearing cold load must not post before bootstrap has resolved the CSRF token, or the server answers 403 and the token is wasted), `needsCSRF`-when-session, shell exemption `/auth/verify`, success = `VERIFY_SUCCESS_STORAGE_KEY` + revalidate + redirect (`/account` signed-in, `/sign-in` anonymous — BOTH consume the key once). Failure states: the terminal 422 token-invalid renders the generic invalid copy; a 429 renders the manual retry button under the page's cooldown; every other failure (500, network, timeout) keeps the token and renders the mapped banner with a retry button. The account page (profile tab) owns the unverified banner + resend (`resendVerification`, `needsCSRF`) + the email-change widget (`changeEmail` from profile-api, current-password re-authentication, 200 swaps `_profile`; `_emailChanged` copy) — the verification surfaces share a SEPARATE `_verifyCooldown` controller (a 30-min bucket must never lock the password form's `_cooldown`). Registration redirects to `/account` — the unverified banner + resend live there.
- Web push settings: the account page's NOTIFICATIONS tab EMBEDS `<push-settings>` (`@features/notifications/ui/push-settings.js`) — the settings surface owns the whole push domain; the account page only hosts it (the second auth→notifications import direction alongside the header's badge event). The component renders NOTHING for anonymous sessions; for an environment that cannot push (no ServiceWorker/PushManager, or no SW registration — every Vite dev session) it renders the UNAVAILABLE LINE instead of vanishing (the section has its own tab now, and a blank tab reads as a broken page).
- Install control: `@shared/pwa/install-control.js` renders as a `<push-settings>` SIBLING, immediately BEFORE it (the second host beside the home donation strip), for signed-in users who never land on the homepage. **The account page's NOTIFICATIONS tab is the host: both live there**, where the ordering and sibling relation are pinned; the element owns its states (deferred-prompt button / iOS share-menu hint / nothing when installed or this browser already allows notifications) and the account page only imports it. The dormant state in test environments is expected (no browser prompt, no iOS UA).
- Follow toggle: `data-access/follows-api.ts` (status GET + add PUT + remove DELETE — writes `needsCSRF`, the favorites mirror) and `ui/follow-toggle.ts` — the detail-page bell (`<follow-toggle kind="blog-posts|projects" content-id=…>`). NO debounce (the shared heart debounce covers LIKES only — a follow toggle is a plain pending-disable), NO event dispatch (follows drive no public counters), renders NOTHING for anonymous or an empty contentId (the favorite-toggle precedent), the `_loadedKey` latch + 403 silent-revalidate healing copied from favorite-toggle.
- Active sessions: `data-access/sessions-api.ts` (list GET — no CSRF; revoke DELETE — `needsCSRF`, idempotent 204) + the `SessionItem`/`SessionListResponse` wire types. The account page's DEVICES tab renders them through `ui/account-sessions-section.ts` under the `el.ui.sessions` heading, with the sign-out actions below them: device label or the `sessionsUnknownDevice` fallback, `formatDate` over the canonical instants (the sessions block keeps the exact long formatter — it needs the instant, unlike the content dates), the `sessionsCurrent` badge on the requesting row (which carries NO revoke button — sign-out owns that), a revoke button elsewhere, local row removal on success, `_sessionsActionError` as a banner ABOVE the list (a revoke failure must not replace the list the way `_sessionsError` does), a retry button for load failures, and a load-more button that CAS-checks the cursor it was issued with — the server default page size is mirrored by `SESSION_PAGE_SIZE`.
