# web/src/features/admin — Agent Navigation

Content administration: the staff-only dashboard (blog + projects tabs), create/edit forms, and the media upload widget.

## Open this file when

- changing the admin surface (dashboard, forms, upload widget), its routing, or the admin data-access contracts.

## Folder-local conventions

- The media upload surface is `data-access/media-api.ts` + the `sf-media-upload` widget. **Choosing a file IS the upload** (no second press), the preview is a large 16:9 block matching the public page's crop, a status line always states the upload state (`uploadStatusNone`/`uploadStatusUploading`/`uploadStatusUploaded`), and the remove control deletes the file THIS widget uploaded via `deleteMedia` (DELETE /api/v1/media/{file} — the `file` is the last segment of the served URL the server returned, never hand-built) before reverting to the row's stored path. The delete is best-effort and SILENT: a 409 (referenced meanwhile) or any failure keeps the file, and the 24 h sweep is the backstop. The blog CRUD surface is `blog-admin-api.ts` (create/staffList/staffDetail/update/delete; mutations need CSRF; update/delete carry `If-Match: "<revision>"` built from the staff detail body's `revision` field — the same value the ETag header carries, since the transport drops response headers), and `blog-form-page.ts` (create AND edit + delete in one element — postId="" selects create; thumbnailPath = the upload widget's value or the loaded post's stored path; a 412 reloads the fresh row and shows the Greek stale copy; a 403 heals through the silent session revalidate). The shared form skeleton (guard, load, the action machine, the 412/403 handling, the delete flow, the widget wiring) lives in `ui/content-form-base.ts`; the two pages extend it and keep their fields, markup, and copy.
- **The form's actions carry the state.** There is NO status select: a live `.state-chip` beside the title states what the row IS (create: what a plain save lands as — a draft), and the buttons name the transitions — «Αποθήκευση» (keeps the row's state; create: `actionSaveDraft`), «Δημοσίευση», and for a published row «Απόσυρση» + «Αρχειοθέτηση». Enter (implicit submit) runs the SAFE save. The state is submitted per ACTION, never read from a field. After a write: published → navigate to the public page (`/blog/{id}` | `/projects/{id}`), archived → back to the list, a draft save stays on the form with the success line, and a CREATE that lands as a draft goes to the list. `_pendingAction` drives the pressed button's pending label.
- Downloads: `download-rows.ts` is the shared add/remove/reorder row editor (the media-upload contract — the parent calls `load(rows)` in edit mode after the ready state renders the widget and `getValue()` at submit; `getValue` maps empty inputs to null and trims; the SERVER validates grammar). Both forms embed it in the downloads field; the blog form passes `rowLabel=el.admin.downloadResolutionLabel` + the "1080p" placeholder, the project form `el.admin.downloadNameLabel`. Both submit the full-replacement array (`resolution`/`name` keyed) and run a LIGHT client guard (a link-less row blocks the submit with the required copy — the server re-validates everything). **The array is required, so ONE row is the floor:** the widget seeds an empty row when loaded with none, and a lone row renders NO action controls at all — the ↑/↓ reorder pair and the remove control both appear only once a second row exists (nothing to reorder, and removal would empty the required array); the row carries `data-solo="true"` so its fields take the tracks the actions would have used, and `_remove` refuses to empty the list (an empty array would pass `isValid()` and reach the server as a 422). Both content types get all of this from the one widget. The DELETE button is admin+-gated in BOTH forms (`_canDelete` = `isContentCreatorRole` — a moderator edit renders no delete button; pure visibility, the server enforces via `CanDeleteContent`).
- The projects surface: `projects-admin-api.ts` (the blog module's counterpart — the CREATE body has NO slug field; the UPDATE body's `slug?` is admin+-only), `project-form-page.ts` (the blog form's counterpart with the admin+-only slug input; a moderator edit never renders the field, so the form cannot submit a capability the session lacks — both pages extend `ui/content-form-base.ts`, and a 412 shows the kind's stale copy: the base's shared default names the blog post, and the project form overrides `_preconditionMessage` with `el.admin.staleProject`), and the dashboard split into `admin-list-base.ts` + two leaves (`admin-page.ts` = `/admin`, `admin-projects-page.ts` = `/admin/projects`).
- The users surface: `users-admin-api.ts` (`listStaffUsers` with role/status filters; `email?` is OPTIONAL — the server omits it for moderator viewers and the client renders it only when it arrives, never guessed from the session role), `admin-users-page.ts` (`/admin/users` — a STANDALONE element, not an AdminListBase leaf: the base is content-shaped with create/edit affordances, and the users page owns two filter params that ride the pager URLs). Its guard, latch, and load-error mapping come from `AdminStaffPageBase`. The member rows are the recorded exception to the content-card rule (components.md rule 15): an interactive management surface — collapsed heads with staged selects and a per-member panel — rather than a content listing. The peer-matrix predicates (manage/status/role options) live in `utils/member-rules.ts` as pure functions of the session state and the row. The member card/panel, the staged drafts, the save (role PATCH + status POST), the reset state and its handlers (the dialog MARKUP stays on the page), and the delete flow live in `ui/member-section.ts`; the page keeps the filters, the load/paging, and the row replacement hooks. The tab chrome lives in `admin-tabs.ts` — every staff tab surface (dashboard, projects, users, metrics, logs) renders it — with its `.admin-tabs`/`.admin-tab` CSS in `admin-tabs.css`; the users page imports `admin-page.css` for the page shell (its own list chrome is `admin-users-page.css`). Filter changes pushState a FIRST-page URL (a cursor is only meaningful with the same filter) and re-sync — the search-page `_pushAndSync` pattern. When `ui/member-section.ts` is next touched, the components.md rule 16 split is pre-authorized — extract the panel/draft block into an `admin/ui/` section controller — and the users-page suite must pass unchanged.
- **The users page is a MEMBER-CARD surface.** Each row renders a collapsed `.member-card`: `.member-head` (avatar, username, email, verification + join date, role/status chips, chevron) opens ONE member's `.member-panel`. A row the viewer may not act on renders `.member-head--static` — no button, no chevron, no empty panel. Role and status are STAGED selects in the panel, committed by ONE `.member-save` that appears only while `memberChanges()` — the module-level diff of row vs draft — is non-null; only the differing fields are sent (role = PATCH, status = suspend/reactivate POST, in that order). The chips read the staged value (`.member-chip--staged`, dashed border), and `_settleSave` applies what the server confirmed while keeping a failed field staged (a two-leg save can land its first leg). A `.member-head` with no actions is inert; the two immediate actions are ICON buttons (`.member-action` + `--danger`) whose meaning rides `aria-label`/`title`, with the pending wording swapped in while in flight. Drafts are dropped on cancel, on panel close, on every `_load` (page or filter change), and when the member is deleted. **The suspend confirmation hangs off the save**: it fires only for a staged active → suspended transition, and a declined confirm keeps the draft.
- The reset affordance: the reset control renders only where the server would ALLOW the reset — the predicate is `_canManageRow` (the same peer matrix reset, role, and delete share; pure VISIBILITY, the server enforces). It is the panel's key-glyph icon button (`aria-label`/`title` carry the meaning, and the pending wording while in flight). A `window.confirm` gates the POST, and the one-time temp password renders once in a `.reset-dialog` (`resetUserPassword` in `users-admin-api.ts`, needsCSRF) — a native modal `<dialog>` (components.md rule 10): `_showResetDialog` runs from `updated()` and is idempotent via `dialog.open`, and Escape routes through the dialog's `cancel` event into the same `_onCloseReset` as the close button. The dialog state clears on page navigation (a page change closes the plaintext) and on close; the copy button writes to the clipboard with a try/catch fallback (the `<code>` is user-selectable).
- Role change + deletion: the reset predicate is `_canManageRow` (the same peer matrix reset, role, and delete share); `_roleOptions` (super-admins pick from `ROLES`, admins from the named `ADMIN_ROLE_CHOICES` constant — the select never offers a capability the session lacks). The role change PATCHes and replaces the row IN PLACE with the server's `StaffUser` projection (email still server-authoritative); a 409 shows `el.problems[\"/problems/auth/last-super-admin\"]` through the shared `_opError` banner. Delete → 204 (confirm with `el.admin.deleteUserConfirm` — the content-survives warning) removes the row locally, drops its draft/panel; when the page loses its LAST row the page steps back via `paging.prev()` if a previous page exists, else re-syncs (a genuinely empty page renders the empty state). A save serializes on `_savingId` (the panel's selects and its save/cancel disable while it is set; the two immediate icon actions serialize per kind on their own ids) and the early-return guard stays as the backstop; each mutation owns its AbortController (`_deleteAbort`/`_saveAbort`/`_resetAbort`), and `_load` clears `_opError` on page changes.
- The status capability is the panel's staged select: `_canChangeStatusRow` mirrors the server's `CanChangeUserStatus` (super-admin everywhere; admin on moderator/user rows; moderator on user rows ONLY), and it is one of the predicates that decide whether a card opens at all: `_canManageRow` and this gate the head's button and the panel's controls, `_roleOptions` fills the role select. A moderator therefore gets a user row's panel with the status select ALONE and no icon actions. Suspension is amber (`.member-chip--suspended` uses `--sf-warning`), deletion stays danger red on the icon button. The three row-action handlers (`_onResetClick`, `_onSaveMember`, `_onDeleteClick`) funnel through ONE `_runRowAction` skeleton (busy-id serialization, confirm gate, AbortController, error slot, conditional busy clear), a load generation discards late success/error effects across a page/filter change, and the suspend confirm hangs off the save (it fires only for active → suspended, once the busy guard lets the save run).
- **A `<select>` whose options are mapped in the same render must carry `data-value`, and the page's `updated()` re-applies it** (`select[data-value]`). Lit commits a property binding before the mapped children exist, so `.value=${...}` silently falls back to the FIRST option (a moderator would read as «Μέλος»). Both filter selects, the panel's role select and its status select go through that one pass; a `data-role` attribute is not needed.
- The metrics tab: `data-access/metrics-api.ts` (`getStaffMetrics` — no parameters, the server derives every number) and `admin-metrics-page.ts` at `/admin/metrics`, plus the fourth `admin-tabs.ts` tab (`metricsTab` copy in `el.admin`). The page is a STANDALONE element (not an AdminListBase leaf): nothing paginates or creates here, so the base's paging controller and row markup would be dead weight; it reuses `admin-page.css` for the shell and adds `admin-metrics-page.css` for the number cards and CSS bars. **The bars' geometry is a GROUP grid:** `.metrics-bars` is one grid (`max-content 1fr auto`, capped at 48rem on the group because a row has no box) and `.metrics-bar-row` is `display: contents`, so a group's rows share three columns: the label cell's own `min-width: 8rem`/`max-width: 16rem` clamp the column to the longest label, and the track takes everything left. A per-row grid sized each row's columns independently — bars at different x positions, and a `minmax` label track that was grown together with the flexible one left the bar a stub on a phone. The title spans `1 / -1`. **The rule-of-three guard extraction**: `admin-staff-page-base.ts` owns the session guard, the authenticated first-load latch, and the load-error mapping for every staff surface (AdminListBase and the users, metrics, and logs pages) — so a below-floor viewer is answered from the guard alone on EVERY surface and no request is made (the 403 branch stays for a server-side floor change). Number rendering is one key per context (`metricsProjects` is its own anglicism key, rendered `lang="en"`), bars are decorative empties beside their numeric text, and the `since` line renders with `formatDate` (an instant, not a date). **The activity rows split into TWO half-width groups** (one 48rem column left the other half empty): the `.activity-breakdowns` wrapper wraps the pair to one column on narrow windows, both groups share ONE denominator (the section's largest counter, so bars stay comparable across the split), and each group keeps the stored cap. Numbers render straight from the payload — never derived from a loaded list, never cached.
- The super-admin logs tab: `data-access/logs-api.ts` (`getStaffLogs` — the level/q/limit query contract, `LOG_LEVELS` + the limit bounds shared with the page) and `admin-logs-page.ts` at `/admin/logs` with `admin-logs-page.css`. It is the FIRST staff surface with a floor narrower than moderator+: the page overrides `AdminStaffPageBase._hasStaffAccess` with `isSuperAdminRole` (mirroring `identity.CanViewLogs`) so a below-floor viewer makes NO request, and `admin-tabs.ts` READS THE SESSION CONTEXT to render the logs tab only for a super-admin — the alternative (a per-page flag) would hide the tab on every page but its own. The tab switch is `replaceState`, not `pushState`: a filter change is not a navigation step, while the filters DO ride the URL so a reload or a shared link keeps the view (`_readURL` ignores values outside the wire contract rather than sending a 422). The result table renders the attributes as JSON and the record count is a tail, not a page — no paging controls, no total, no polling. Both tables print instants with `formatDateTimeNumeric` (the blogs/projects format); the audit table's technical headers are English and rendered inside `lang="en"` — `timestamp`, `Actor (ID)`, `Target (ID)`, `Request (ID)`, `Address` — while the log tail keeps its Greek level/message/fields headers. The audit id columns name the value kind (the `(ID)` suffix; the address column says what its value is too), because the bare words did not tell a hash from an address.
- The audit browser is the logs tab's SECOND section: `data-access/audit-api.ts` (`getStaffAuditEvents`, the `AUDIT_EVENTS` vocabulary that `internal/audit/event_names_pin_test.go` pins equal to the Go list, and the 50/200 limit bounds) plus the audit half of `admin-logs-page.ts`. The two sections are INDEPENDENT reads — separate filter sets, states, and AbortControllers — so a failed audit read never blanks the log table; a 403 from EITHER flips the page to forbidden, because that is the server's floor moving rather than a section failing. The audit filters use their own URL params (`aevent`/`alimit`) written by the same `_syncURL`, and the event labels come from the `el.admin.auditEventNames` map (an unknown key falls back to the wire value, and nested catalog groups are now checked recursively by `el.test.ts`).
- The dashboard tabs are TWO ELEMENTS, not one element with an internal tab switch: the router REUSES an element instance across same-route navigations, and the shared `UrlCursorPagingController` keys its re-sync on the page path — a path-switching element would have to outrace the controller's own navigate-event listener. Separate routes → separate elements → each page has one fixed path and the controller's wiring works untouched. The shared base owns the guards, tab chrome, list/pager markup, and states; each leaf binds its API call, addresses, and the per-row secondary line (projects show the slug).
- **Each row is a `<content-card shape="row" dense>`** with `heading-level="0"` (the title stays text — the list already names the rows), the status chip as `badge`/`badge-tone` (`draft`/`published`/`archived`), `subtitle` for the blog rows' inline line (projects have none), `secondary` for the slug, the clamped description, and the `meta-label`/`meta-instant` topline pair; the edit link is the card's `slot="actions"` child, so the page styles only the anchor (`.edit-link`) and the card lays it out at the row's end.
- **The admin rows take the card's normalisations** — an accepted ruling, not a page-local style (components.md rule 15: a caller never restyles a shape): the status chip rides the top line beside the update instant, the title wraps, the text column top-aligns, the description uses the muted text token the favorites/search rows use, and the row follows the shared narrow-screen rules (the thumbnail steps down at ≤700px, the row stacks at ≤480px).
- The base's config is prototype GETTERS with throwing defaults, never class fields: the base constructor builds the paging controller before leaf field initializers run.
- The write field is `thumbnailPath` (STORAGE-relative) — never hand-built: the upload response's `path` or the staff detail's `thumbnailPath` feed it. The absolute `thumbnailUrl` cannot be converted back to the storage form.
- Staff gating is CLIENT-SIDE VISIBILITY ONLY (role from the session context) — the server enforces authorization (role checks + CSRF + origin + the draft-visibility gate). Never rely on hidden UI for protection. The one place the client predicate is load-bearing is the base's first-load latch: it decides whether the server is asked at all, so `_hasStaffAccess` must mirror the server's floor (pinned by `admin-staff-page-base.test.ts`).
- The widget's contract: `getValue()` returns `{path, url} | null` (the server-returned storage path is what the form submits as `thumbnailPath` — never hand-built); `isUploading()` is true while a chosen file is in flight, and BOTH forms refuse to submit then (`el.admin.uploadInFlight`) because the value still holds the PREVIOUS thumbnail; `reset()` clears file/input/preview/value; the upload starts on file CHOICE and a new choice aborts the previous upload. It dispatches `media-upload` CustomEvent on success; a failed replacement keeps the previous confirmed value (with none, the value stays null), so the form keeps the stored thumbnail and the status line reverts to it. The status line is the ONLY upload-state copy on screen — one line, no second success note.
- **The state chip states what the row IS; only a server response moves it.** A failed write (422/500/network) leaves the chip and the action set exactly as they were, so the next «Αποθήκευση» still submits the row's real state — the chip is never advanced to the attempted target before the request lands.
- **The content lists are FILTERABLE.** `AdminListBase` renders one filter row for both tabs — a status `<select>` and a title `<input type="search">` with an apply button — and every list URL builder carries the two params (`status`, `q`), so a cursor is never separated from the filter that produced it. The server splits `q` into words and ANDs them, so `dr stone` finds `Dr. Stone` (the client sends the query as typed — it never folds or splits it). A filter change `pushState`s a FIRST-page URL and re-syncs (the users-page `_pushFilterAndSync` pattern; the page size also returns to its default, exactly as there). The row is ONE filter set and input is never dropped: the text applies on submit, and a STATUS change carries text that was typed but not yet submitted (`_typedFilter` reads the field). The text filter never runs per keystroke — every keystroke would be a request AND a history entry. `onLoad` re-reads both from the URL; a status outside `CONTENT_STATUSES` and a `q` longer than `MAX_FILTER_QUERY_LEN` are IGNORED rather than sent (the server 422s either). The status select goes through the page's `select[data-value]` pass in `updated()` WITHOUT an empty-value exception — "every status" is a real selection the user must be able to return to — and the option check keeps a select without that option from being blanked; the title input has no value binding at all and is written only when it is unfocused and stale (a FOCUSED field is never touched). The row is DISABLED until the list is live (`?disabled=${this.status !== "success"}` on all three controls): the documented client floor means a below-floor viewer must never ask the server, and an enabled control would fire one 403 per touch (the users-page precedent). An empty result under a filter says `listEmptyFiltered` instead of claiming the site has no content.
- **Nothing in the admin surface may overflow the page.** The admin sheets keep their phone-safe holds: `download-rows.css` keeps `minmax(0, …)` link tracks (a grid paints its track minimums whatever its container is) and stacks the row at ≤700px by named `grid-template-areas` (the children carry the area classes: `.download-magnet`, `.download-torrent`, `.row-up`, `.row-down`); `admin-tabs.css` scrolls (`overflow-x: auto`, `max-width: 100%`, tabs `flex: 0 0 auto` + nowrap) exactly like the account page's section tabs; both form sheets wrap their `.form-header` and `.form-actions`. The shell carries the class-level guard (`css.md` rule 9); anything in the admin route that still overflows is the owning component's fix. The pins for all of this read the raw stylesheets — happy-dom resolves no CSS.
- The admin list rows render the favorites card shape: thumbnail, title with the status badge, a clamped description, and `Ενημερώθηκε · <numeric date>` — the shared `formatDateTimeNumeric`, never the raw ISO instant. The meta line renders only when `updatedAt` is present (a dangling separator is not a contract). The row's edit affordance is the ICON pencil (`icons.edit`) with `aria-label` + `title` = `el.admin.edit` — the same shape the blog/project detail pages' `.admin-edit-link` wears.
- The list surfaces' loading, EMPTY, and ERROR states all sit in the shared `.state-block` (`core/styles/baseline.css`) — an error that replaces the empty box must not resize the region under the tab row either.
- Object URLs (`URL.createObjectURL`) are revoked on replace/remove/teardown — never leak them past the widget's lifetime.
- Greek copy lives in the catalog `el.admin` group — no literals here (root rule 9).
