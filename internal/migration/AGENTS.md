# internal/migration — Agent Navigation

Legacy export → target SQLite transform and reconciliation reporting. This is migration tooling, NOT the runtime store — runtime queries belong to `internal/store`.

## Open this file when

- changing the legacy source shape, the mapping rules, or the reconciliation report.

## Folder-local conventions

- CONTENT rows receive DERIVED 32-hex IDs: `hex(HMAC-SHA256("sick-fansubs:legacy-content-id:v1", legacyObjectId))[:32]` in `ids.go` (`deriveTargetID`). Determinism is the contract for the derived content and preserved user IDs: the favorites import resolves legacy references with no saved mapping state, and a fresh-target re-import derives identical content IDs. CHILD rows: blog download rows get fresh random IDs at import (`id.New`); project batch rows PRESERVE the legacy sub-ObjectId when present (`project.go`) and mint fresh only when absent — the 24-hex legacy shape is the `ids.md` rule-3 migrated-identifier case. USER rows are the exception: they PRESERVE the legacy ObjectId as the target ID, so their report entries are identity pairs. Legacy timestamps are preserved so `published_at_ms` keeps the legacy ordering.
- Missing/unparseable or non-positive `dateTimeCreated` falls back to `created_at_ms` with a warning; `created_at_ms` derives from `createdAt` when present, else from `dateTimeCreated` with a warning — a record with NEITHER usable value REJECTS (never fabricated). The fallback chain applies to BOTH content kinds: projects have NO `createdAt` in the real export (none on all 22 production records), and most blog posts lack it too — only 32 of 333 rehearsal records carried it (301 of 333 without). Records that would violate target NOT NULL/CHECK constraints (empty `title`/`thumbnail`/`slug`) also REJECT per-record with a concise reason — never a raw CHECK abort of the whole import.
- Download classification is present/empty/absent/malformed; malformed values are preserved as-is with a warning — never silently discarded.
- Creator/updater ObjectIds resolve against imported users; orphans are reported and the reference stays NULL — never fabricate a user.
- Reports carry counts, source IDs, and concise reasons — never full records or sensitive values. Empty report sections marshal as `[]`, not `null` (pinned by test) — the reconciliation, media, and avatar reports alike; a clean media/avatar run still carries an empty `failures` array.
- The SQL in `import.go` is tool-owned (one-time import), not the runtime store boundary. Search index rows are written in the SAME transaction as the content row via `store.IndexBlogPostTx`/`store.IndexProjectTx` — only rows with a publish time are indexed; the normalized index text is computed by `internal/search`, never raw SQL.
- Media import (`media.go`): the stored legacy URL is the join key — clean legacy MinIO forms (`/media/images/<key>.<ext>`) keep the object key, and every OTHER absolute URL derives `x-<sha256(url)[:32]><.ext>` (the production data hosts most blog thumbnails on external CDNs — 264 postimg, 37 Discord, 54 legacy-host). Only non-absolute values are `badReferenceShape`; the hash key is the join only — media IDs stay content-derived (`MediaIDForBytes`), so the immutable-cache contract survives changed bucket objects; source reads enforce `media.MaxInputBytes`; a re-run over an already-rewritten database selects no rows (the query matches only non-`media/` references), so media import re-runs are idempotent; failures are counted with stable reason codes (never URLs/keys in reports). The total-pixel bound applies to imports too: `processFailureReason` maps `media.ErrPixelsTooBig` → `pixelsTooLarge` (same deliberate-bounded-reject policy as `oversizedSource`/`dimensionsTooLarge`).
- Avatar import (`avatar.go`): `ImportAvatars` mirrors the media import with ONE structural difference — the join is EXPORT-side: the users import defers `avatar_url` to NULL, so the legacy URL never enters the target DB. The command reads the users export and passes an ObjectId→URL map; `ImportAvatars` matches `users.id = ? AND avatar_url IS NULL` (unimported/rejected users are skipped silently — counted nowhere), processes through `media.ProcessAvatar` (the avatar pipeline — 200×200 PNG, NOT the thumbnail one), rewrites in place, and reports counts only (never URLs/user ids). Per-object failures are counted, never fatal; per-object commits make interruption safe.
- Projects: `readLegacyRecords[T]` in `reader.go` is the one generic reader — both blog and project files go through it; add a shape via a typed wrapper, never a copy. Leading whitespace is tolerated to 4096 bytes; a JSONL record line is bounded at 1 MiB (the array path is not line-bounded). The project transform pre-validates the NUMERIC CHECKs too (`created_at_ms > 0`, `updated_at_ms >= created_at_ms`, `published_at_ms > 0`): non-positive or inverted instants reject per-record (or fall back with a warning for the publication instant) — parseability alone does not clear the CHECK. The blog transform carries the identical guard. The duplicate-slug map and SQLite's UNIQUE(slug) agree on case-sensitivity (BINARY): slugs differing only by case are distinct rows, not duplicates.
- Users (credential migration): user IDs are PRESERVED legacy ObjectIds — the report's source→target entries are identity pairs (unlike content's DERIVED ids). Verifiers are preserved byte-for-byte in EVERY category; `auth_version` starts at 1 for every imported user; `classifyVerifier` (user.go) feeds the report only — the runtime gate (`service.verifyPassword`) decides what sign-in compares, and the classification constants here mirror the service's. Avatars are deferred to the avatar import: counted (`avatarsDeferred`), stored NULL — never the stale MinIO URL. Canonical keys (lowercased username/email) collide on a per-record rejection basis (first record wins); UNIQUE violations at INSERT are likewise per-record, not operator-stopping. Timestamps: a missing/unparseable/non-positive createdAt falls back to updatedAt with a per-record warning (the mirror of the existing reverse fallback) — a record with NEITHER timestamp usable still rejects "missing or invalid createdAt"; a parseable-but-non-positive updatedAt rejects "invalid updatedAt"; created/updated inversions equalize up to `maxClockSkewMS` (5 min) and reject beyond. Users import BEFORE content — creator/updater resolution depends on it. The favorites arrays on `LegacyUser` are decoded but IGNORED by the users import — the favorites import owns them (below).
- Favorites (`favorites.go`): `ImportFavorites` reads the USERS export and MUST run AFTER users + content. Per user, one immediate transaction: the anchor is the IMPORTED `users.updated_at_ms`, the LAST array entry lands on it, and earlier entries step back 1 ms per position (preserving legacy recency order under `created_at_ms DESC`), clamping at 1 ms with a warning (the `created_at_ms > 0` CHECK). Everything is resolved IN-TRANSACTION (user + content existence), so `INSERT OR IGNORE` can only ever trip the composite PK — counted `alreadyPresent`, never an error. Skips are counted, never fatal: `userMissing` (rejected/absent user), `contentMissing` (derived id not in the content table). The report's `favorites` section carries per-kind `users`/`sourceRows`/`imported`/`alreadyPresent`/`userMissing`/`contentMissing`.
