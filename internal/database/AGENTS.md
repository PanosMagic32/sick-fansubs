# internal/database — Agent Navigation

SQLite connection lifecycle: DSN construction, pool, WAL, pragma verification, embedded migrations, strict/maintenance openers, readiness checker. The foundation rules live in [`docs/patterns/go/sqlite.md`](../../docs/patterns/go/sqlite.md).

## Open this file when

- changing openers, DSN/pragmas, pool settings, migration files or runner logic, or the readiness check.

## Folder-local conventions

- Opens go through `openDSN` (`sqlite.NewConnector` + `sql.OpenDB`); the driver package is imported
  for its API — never blank, and never the `sqlite3` driver-registration name (the
  `TestDriverNameAndDSNConfined` guard bans that literal tree-wide, together with the `_pragma`
  confinement below).
- Migration-aware openers: `OpenApplication` (strict exact history — the serving process) and `OpenMaintenance` (applies + verifies — the migrate command). `Open` is the ad-hoc/test opener. Every opener refuses a data directory with group or other access (`openDB`; POSIX only — Windows skips the mode check).
- The Go-declared `schemaSpec` (schema.go) mirrors the embedded migrations — every table/column/index change in a `.sql` file MUST update the spec, or every migrated database fails verification (schema verification fails closed by design). `VerifySchema` runs in readiness and after maintenance opens; `VerifyForeignKeys` runs only in explicit maintenance and import flows — the migrate command, the import commands, and the staged restore — never in readiness (`docs/patterns/go/sqlite.md` rule 10).
- `schemaSpec` index entries verify column DIRECTION too: a descending column carries a `" DESC"` suffix (the `user_notifications` `idx_user_notifications_recipient_created` carries `created_at_ms DESC`; migration 0010's `_post_top` comment indexes extend the set); `readIndexColumns` captures the index_xinfo desc flag, so a hand-flipped direction is a fail-closed drift.
- Migration 0008: `users.must_change_password INTEGER NOT NULL DEFAULT 0 CHECK IN (0,1)` and `audit_events.target_role TEXT NULL` — both schemaSpec-pinned (ALTER TABLE ADD COLUMN requires the non-null default, which also backfills migrated rows).
- Migration 0010: `blog_post_comments`/`project_comments` + heart join tables + `user_notifications` — the first DECLARED partial index (`idx_user_notifications_unread … WHERE read_at_ms IS NULL`). The verifier accepts partial indexes only when an indexSpec declares `partial: true` (schema.go's indexSpec, schema_verify.go's `indexSatisfies`); an undeclared partial index still fails as "unexpected". Migration 0013 REBUILDS `user_notifications` to widen the kind CHECK to `('comment_reply','heart')` — the 0010-comment table-rebuild contract (never edit the old .sql — checksummed history); no column/index change, the verifier spec is untouched.
- Migration 0014: `push_subscriptions` (endpoint UNIQUE; `idx_push_subscriptions_user` for the fan-out lookup) + `notification_preferences` (composite PK `(user_id, kind)`, kind CHECK `('heart','comment_reply')` — new kinds amend the CHECK per the 0013 contract). Both schemaSpec-pinned.
- Migration 0015: `content_follows` (composite PK `(user_id, content_kind, content_id)`, polymorphic content ref with NO content FK — the user_notifications precedent; `idx_content_follows_content` for the emitter lookup) plus TWO CHECK-rebuilds — `user_notifications` widens its kind CHECK to `('comment_reply','heart','comment','content_updated')` and makes `comment_id` NULLABLE with a per-kind table CHECK (`kind = 'content_updated' OR comment_id IS NOT NULL` — the schemaSpec column entry flips notNull to false); `notification_preferences` widens to the same four kinds (columns unchanged, no spec change). All schemaSpec-pinned.
- Migration 0016: TWO kind-CHECK rebuilds only — `user_notifications` widens to `('comment_reply','heart','comment','content_updated','new_content')` with the per-kind rule `(kind IN ('content_updated','new_content') OR comment_id IS NOT NULL)`, `notification_preferences` widens to the five kinds. No column/index change — the schemaSpec is untouched. Each table keeps its OWN historical CHECK order (the 0015 header contract).
- Migration 0017: TWO kind-CHECK rebuilds only — `user_notifications` widens to the six kinds (`comment_removed` appended) and `notification_preferences` likewise (`('heart',…,'comment_removed')`). No column/index change, so the schemaSpec stays untouched; the per-kind `comment_id` rule is unchanged (the kind carries the deleted comment's id, which dangles by design — no FK).
- Migration 0018: ONE `ALTER TABLE sessions ADD COLUMN client_label TEXT` — the optional closed-vocabulary device label the classifier writes at session creation. Nullable, NO CHECK (the vocabulary lives in Go — a SQL copy would drift), no index (the list filters on the already-indexed `user_id`), no backfill (a label exists only when a sign-in observed a user-agent; existing rows stay NULL). The schemaSpec's `sessions` entry gained the column — the 0008/0012 ADD COLUMN precedent, and a spec that misses it fails verification closed.
- Migration 0019: TWO kind-CHECK rebuilds PLUS one new nullable column — `user_notifications` widens to the seven kinds (`draft_activity` appended), gains `draft_action TEXT` bound to that kind by an iff CHECK (`(kind = 'draft_activity') = (draft_action IS NOT NULL)` and the three-action vocabulary), and widens its per-kind `comment_id` rule to exempt the new kind (it names no comment); `notification_preferences` widens to the same seven. The schemaSpec's `user_notifications` entry gained `draft_action`. One migration, both tables — the 0016/0017 shape with a column.
- Migration 0020: TWO index drops — `idx_audit_events_target` (no shipped query predicates on `target_id`; the feed filters by event and the role snapshot) and `idx_projects_slug` (a duplicate of the UNIQUE auto-index on the same column). Their schemaSpec index entries were removed with them.
- Migration 0021: ONE `ALTER TABLE notification_reads ADD COLUMN dismissed_at_ms INTEGER CHECK (dismissed_at_ms > 0)` — the per-viewer dismissal stamp behind the feed's delete-on-a-ledger-row (a dismissal always stamps `read_at_ms` too). Nullable on purpose: an ordinary read row keeps NULL. The schemaSpec's `notification_reads` entry gained the column; the table stays STRICT (the 0018 ADD COLUMN precedent).
- The embedded migration files are checksummed history: never edit an applied `.sql`. That immutability is also the one recorded exemption to the decision-citation check — a comment inside `migrations/**` may cite a retired decision record, while no living file may (`docs/patterns/go/sqlite.md` rule 8).
- `collation.go` registers the search collation (`search.CollationGreek` = `sf_greek`) with the driver in an `init()`, before any `sql.Open` — the driver applies registered collations to connections opened AFTER registration, so a later registration would leave already-open connections with "no such collation sequence" (pinned by `TestSearchCollation_RegisteredBeforeOpen`). A duplicate name is a programming error, so the `Must` variant's panic is the correct failure here — the accepted exception to the rule that setup errors return to main (the name is a package constant; only a rename collision could trigger it, and the alternative is a process that serves 500s on every search query). The comparator lives in `internal/search` (that package stays driver-free); this package depends on `search`, never the reverse. The collation is never part of a schema or index definition — only `ORDER BY`/keyset predicates name it — so the schema verifier, backup, and restore stay unaware of it.
- `functions.go` registers the SECOND driver extension: `sf_fold(text)` (`search.FunctionFold`), a deterministic scalar function returning `search.Fold(text)` — the staff content filter's title match. Same rules and same reasons as the collation: registered in an `init()` before any `sql.Open`, panics on a duplicate name, implemented in the driver-free `internal/search` so there is ONE fold rule (SQL and Go can never disagree — the `TestFoldFunction_*` canaries). A NULL argument answers NULL. The store splices the NAME (a package constant) into `instr(sf_fold(title), ?)` — ONE call per query word — and binds the pre-folded needle; pure SQLite cannot fold Greek (`lower()` is ASCII-only, no diacritic stripping), and a denormalized folded column would need a migration plus a backfill for a filter over hundreds of rows.
- FTS5 virtual tables (migration 0005): schemaSpec entries for `blog_post_search`/`project_search` use `fts: true` — verified as "present and virtual", never STRICT, with no column/index checks (SQLite owns the shadow-table shapes; `PRAGMA table_list` reports them as type `shadow` and the verifier deliberately does not capture them).
- Backup (backup.go, with the offline-restore half and its file helpers in backup_restore.go — the online-backup half of `docs/patterns/go/sqlite.md` rule 11): the modernc `*sqlite.Conn`/`*sqlite.Backup` never escape the `Raw` callback — access goes through the private `backupDriverConn` interface. `Finish` runs exactly once (defer + explicit success call). Page batches of 128 with a deadline check between steps and bounded BUSY/LOCKED retries. The shared `createBackupCore` serves three variants: `BackupForMigration` (contiguous-PREFIX history, `data/backups/pre-migrate-<millis>.db`), `BackupForDaily` (EXACT history, caller-chosen destination dir + filename), and `BackupForPreMigration` (the deploy trigger's rollback unit — the daily unit layout with contiguous-PREFIX validation, because the deploy backup runs before the deploy's migration and the live database can be an older prefix of the NEW backup image's embedded set); all three refuse while a restore marker exists — the unready-window gate. Temp names are unpredictable, artifacts are 0600, validated by independent reopen (prefix or exact history per variant + quick_check `ok` + zero FK violations) before fsync + same-filesystem rename + dir sync. `fullIntegrityOK` (one `integrity_check` `ok` row, backup_restore.go) is shared with restore activation — restore activation requires it.
- Backup validation (step 2, fail-fast before the marker): `StagedRestore` validates a PRIVATE COPY of the artifact (`verifyBackupCopy` — a `.verify-backup-*.db` temp file in the data directory), because the artifact is WAL-mode (the online backup API copies the source's journal mode) and its read-write validation open needs sidecar files. The original artifact is only ever READ — so a restore works from a read-only unit mount (pinned by `TestStagedRestore_ReadOnlyUnitDirectory`: a `mode=ro` attempt fails on the WAL -shm and leaves sidecars behind). `verifyBackupArtifactWith`/`verifyBackupForRestore` open read-write on a writable copy by design — they never mutate the file's content, but WAL sidecars are legal next to the copy and cleaned on close.
- `RestoreOfflineBackup` (backup_restore.go) is ONLY safe while every process has the live database closed (the migrate command owns that window); it needs no session/security reconciliation because its backup is created moments before the migration and no application writes happen in between. Restoring OLDER backups goes through the full staged restore — never call this for that. A crash between its quarantine renames and activation leaves `.broken-<millis>` remnants with no live main; `openDB` then refuses to create an empty database in their place (`ensureNoInterruptedRollback`), and the operator recovers the live file from the remnant by hand.
- Staged restore (restore.go with the activation half in restore_activate.go, the marker/record files in restore_marker.go, and the security reconciliation in restore_reconcile.go — the staged-restore half of `docs/patterns/go/sqlite.md` rule 12): `StagedRestore` is the marker-gated workflow for older backups. Conventions: the marker gate lives in `OpenApplication`, `DBHealthChecker.Check`, and the maintenance surface (`OpenMaintenance`, `MigrationStatus`) via `ensureNoRestoreMarker` (fail closed BEFORE touching SQLite); `openMaintenance` is the marker-EXEMPT path the workflow uses to open its own operation subdirectory; `Open` stays the ad-hoc/test opener. The marker records the attempt millis, and the per-attempt activation record (`restore.activated`, written immediately before the promotion rename, removed with the marker) is the ONLY evidence that the current attempt activated — resume ignores every operation directory named before the attempt (a retained quarantine from an earlier restore never counts). Resume states: live main present + current record → re-run the hook (idempotent), re-verify, finish; live main present without a record → abort (roll a sidecar-only partial quarantine back, discard the staged leftovers, remove the marker), EXCEPT a current-attempt quarantine holding the main file, which fails closed for manual recovery; live main missing + current-attempt quarantine + staged copy → `resumeActivation`; anything else, including a marker from an older layout without `attempt=`, fails closed for manual recovery. The activation record is cleared BEFORE any rollback starts (and its removal failure is itself fail-closed), so an interrupted rollback can never be read as a completed activation on the next run. The security reconciliation v1 compares `audit.AccountSecurityEvents` (success only) via a `mode=ro` read (inspection never mutates the live file); quarantine dirs are RETAINED on success as the rollback set (`.quarantine-<millis>` — the operator removes them); pre-activation failures remove the marker again (live provably untouched — the documented deviation), post-activation failures leave it. The package never logs — `cmd/restore` logs and prints the retained quarantine path.
- `StagedRestoreOptions.PostActivation` is the media slot: a plain `func() error` hook, nil = current DB-only behavior. It runs after `activate()` succeeds and before `completeActivation()` removes the marker — on the normal path AND on every activation-completing resume path (`resumeRestore`'s completed-activation branch, `resumeActivation`). A hook failure retains the activated database and the marker (no rollback) — the hook must be idempotent and a re-run resumes. The package stays media-free: `cmd/restore` wires `media.ExtractMediaTar` into the hook. The hook is NOT invoked on pre-activation failures.
- Reset-token purge: `stageAndPrepare` deletes `FROM password_reset_tokens` and `FROM email_verification_tokens` in the SAME transaction as the sessions purge (verified by `resetTokensEmpty` and `verificationTokensEmpty`) — a restored older backup must not resurrect a consumed link. `audit.AccountSecurityEvents` gained `password_reset_completed` so the reconciliation sees self-service resets (the list is the reconciliation contract — check the audit package when touching restore).
