# internal/auth — Agent Navigation

Business rules and orchestration (the `Service` type today): validation, password verification, session lifecycle decisions, atomic multi-step workflows. No HTTP, no raw SQL.

## Open this file when

- changing sign-in/registration/password/sign-out behavior, bcrypt handling, or session creation policy.

## Folder-local conventions

- **Error vocabulary (docs/patterns/go/errors.md):** every sentinel and `FieldError` lives in `errors.go`, declared with `errors.New` and tested with `errors.Is`; `FieldError.Unwrap` returns `ErrValidation`, so a category check and a structured extraction both work. The handler maps the vocabulary through `writeAuthError` (`internal/handler/errors.go`) — never add a handler branch for a new sentinel without adding it to that table.
- bcrypt NEVER runs inside a SQLite write transaction; the sign-in rehash + session insert must stay ONE store transaction (`RehashPasswordAndCreateSession`).
- **Test seam:** the hash-GENERATION cost lives on `Service.bcryptCost` (`New` sets the production default 12); same-package tests use `newTestService`/`newTestServiceWith` (cost 4) so success paths hash in ~30 ms. Verification cost is read from the STORED hash — the seam never weakens a comparison. The rehash GATE compares against the same field (`cost < s.bcryptCost`), so a lowered cost cannot turn sign-ins into a perpetual rehash loop. TWO tests deliberately keep the real constructor because they PIN the production cost: `TestRegister_PasswordIsHashed` (the `$2a$12$` prefix) and `TestSignIn_RehashLowCostVerifier` (the rehash target 12) — never route those through the seam.
- Registration's auto-sign-in is ONE store transaction (`CreateUserAndSession`): user insert + first-session insert under version 1 — a failed session insert rolls the account back. bcrypt runs in the service BEFORE the transaction.
- `SessionLifetime` lives here — the handler derives cookie Max-Age from it; never duplicate the value.
- Password reset: `Service.ResetPassword` generates the 16-character temp password (`generateTempPassword` — `crypto/rand`, rejection-sampled from the unambiguous alphabet `tempPasswordAlphabet`), bcrypt-hashes it OUTSIDE the store transaction, and calls `store.ResetUserPassword`. The plaintext returns once for the operator; never log it. The handler and `cmd/resetpassword` share this method. `SignIn` returns `mustChangePassword` as its fourth value, so the sign-in response can carry the flag.
- Self-service reset: `ForgotPassword` sweeps expired tokens first (bounded batch, AFTER the chain's rate-limit gates — the handler runs the limiter before the service), runs the dummy bcrypt on the no-send path, mints via `generateSessionToken`, commits the token row BEFORE the send, and returns (userID, err) — err non-nil only on store/send failure. The sender is REQUIRED on the API surface; `nil` turns an accidental call into an honest error (the admin surfaces pass nil). `ResetPasswordWithToken` validates TOKEN EXISTENCE before password policy (a never-issued token + weak password answers token-invalid, no field leak), bcrypt runs outside the store tx, and the store's CAS handles the races. `validateNewPassword(field, password)` is the shared policy helper (Register/ChangePassword/reset — rule of three).
- Session device label: `clientlabel.go` holds `sessionClientLabel(userAgent)` — the ONE place a user-agent string is interpreted, and the reason the raw header is never stored or logged. The output is a closed vocabulary: a browser family and/or a platform family joined by " · ", or `""` (stored as SQL NULL). ORDER IS THE CONTRACT inside both token tables (Chromium browsers all carry `Chrome/` and `Safari/`, iOS UAs carry `like Mac OS X`), matching is a plain `strings.Contains`, and the bound `sessionClientLabelMaxLen` is a guard rail pinned by test rather than a truncation point. `SignIn` and `Register` each take the raw `userAgent` and classify it themselves — handlers pass `r.UserAgent()`, so no caller can smuggle raw text into the column. Known source limits: iPadOS 13+ and recent macOS Safari share the desktop template and can classify as macOS.
- Imported-username sign-in: migrated usernames keep their legacy spacing, so after an exact `UserByCanonical` miss `SignIn` retries through `store.UserByCanonicalLenient` (exact wins; an ambiguous normalized match wraps `ErrNotFound`). `lookupIdentifier` (self-service recovery) retries the same way, and `cmd/resetpassword` calls the lenient lookup itself — an ambiguous match tells the operator to use the exact spelling. The identifier-keyed rate limiters key on `store.NormalizeCanonWhitespace`, so spelling variants of one account share one bucket. Registration uses the SAME fold (trim + collapse; ASCII letters/digits with single inner spaces, 1–32 bytes) and refuses a whitespace near-duplicate as `ErrUsernameTaken` — including a name several legacy rows normalize alike (`store.IsAmbiguousUser`); `internal/migration`'s `conformingUsername` mirrors the rule for its inventory report.
- Email verification + change: `SendVerificationEmail(userID)` is the shared mint+send (sweep → `generateSessionToken` → `CreateVerificationToken` commit → `mail.VerifyEmail` send; the token-row commit precedes the send). Registration and the email-change HANDLER call it AFTER their commits and log a failure without failing the operation (the resend surface recovers). `ResendVerification` no-ops for verified users, and `IsEmailVerified` is the handler's pre-bucket check for that no-op. `VerifyEmail(token)` shape-checks (43-char base64url) → advisory existence read → the consume transaction, and returns `(userID, role, changed, err)`: `changed` gates the audit. `ChangeEmail` re-authenticates with the CURRENT password (the email is the recovery identifier), validates with the registration rule, no-ops on the same email, rejects an email equal to another account's legacy `username_canon` — resolved through the same lenient lookup sign-in and recovery use, so a whitespace-variant canon still shadows and an ambiguous match is taken; the account's own returned row is the one exemption — then CAS-swaps via `store.ChangeUserEmail` (stamp reset + both token tables deleted in one tx) — returns `(u, previousEmail, changed, err)` so the handler skips the sends/audit on the no-op, mails the verification link to the NEW address, and sends `SendEmailChangeNotice(previousEmail, newEmail)` to the PREVIOUS address (logged, never surfaced). Registration applies the same lenient `username_canon` shadow rejection (ambiguity is taken too). The reset path stamps `email_verified_at_ms` via the store's COALESCE.
