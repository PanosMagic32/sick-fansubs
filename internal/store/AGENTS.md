# internal/store — Agent Navigation

SQLite persistence: user + session + content + search + notifications + push + comments + follows + audit + metrics stores. Purpose-built atomic operations own `sql.Tx`; handlers/services never receive a transaction object. One deliberate seam: tx-scoped helpers (suffix `Tx`, first parameter `tx *sql.Tx`) join a CALLER'S larger business transaction — the import tool and future CRUD must commit a content row and its search index atomically, so the store contributes its SQL to the caller's transaction while the caller owns begin/commit.

## Open this file when

- changing session/user/content/search persistence, transactions, the auth_version revocation discipline, or the FTS5 index maintenance.

## Folder-local conventions

- **Error vocabulary (docs/patterns/go/errors.md):** every sentinel lives in `errors.go`; callers test identity with `errors.Is` (never `==`), and the handler layer owns the public-outcome mapping (`internal/handler/errors.go`). The `IsUniqueViolation`/`isForeignKeyViolation` driver-TEXT checks are the recorded narrow exception: SQLite exposes no typed constraint error there, and each is canary-pinned by its test.
- **SQL mapping (docs/patterns/go/sql-mapping.md):** the `null*` family is declared once, in `null.go`, and `TestNullFamilyConfined` (internal/codestyle) keeps it single-homed. The staff scans' NULL discipline is the scope's local contract: every nullable column scans into a `sql.NullString`/`NullInt64` target, never a plain string (the staff-form 500 precedent). Timestamps come from the caller or the operation's `Now` field — the time rules live in the same pattern doc.
- **Identifiers (docs/patterns/go/ids.md):** every store mint calls `id.New` (`eventID`/`downloadID`/`notificationID` sites); `TestStoreDoesNotImportMedia` keeps the store free of media code.
- Session creation is conditional `INSERT…SELECT` against `users.auth_version` + `status='active'` — new session paths must keep that guard (`auth_version` equality is THE revocation mechanism).
- The disambiguation SELECT after a 0-row UPDATE is a documented benign TOCTOU — keep the comment when copying the pattern.
- `DeleteExpiredSessions` is one bounded batch (LIMIT subquery); the multi-batch loop lives in `cmd/api`.
- `UpdateUserPassword` and `CreateUser` have no store-level writer: neither has a production caller — password changes go through `UpdatePasswordAndRevokeSessions`/`ResetUserPassword`, registration through the atomic `CreateUserAndSession`, and the sign-in rehash through `RehashPasswordAndCreateSession`. Tests that need a bare user row seed one through `internal/store/storetest` (`storetest.InsertUser`), which is test support and never imported by production code. `DeleteSessionsByUserID` and `IncrementAuthVersion` have no store-level writer: every session-revocation path pairs the bump + delete atomically in `IncrementAuthVersionAndDeleteSessions`/`SuspendUser`/`ReactivateUser`, so a standalone delete is never the right primitive.
- Tests use `openStoreDB` + `mustCreateUser`/`mustCreateSession` against a real migrated temp DB; `mustCreateUser` delegates to `storetest.InsertUser`.
- Blog list: the keyset pattern is TWO explicit query shapes — first page has no continuation predicate, later pages apply `published_at_ms < ? OR (published_at_ms = ? AND id > ?)`. Fetch `limit+1` rows so `hasNextPage` needs no count query. The public filter is `status='published' AND published_at_ms IS NOT NULL`; only the `published_at_ms IS NOT NULL` half matches the Go index writers (`search_store.go` indexes any row with a publish stamp, no status condition), so don't cite it for the status half.
- Blog list projection: the list row carries description, updated_at_ms, and the creator ref (LEFT JOIN users, aliased `p.`/`u.` everywhere — the join adds a second `id` column, so unqualified names would be ambiguous). `nullStringPtr` maps nullable columns to pointers.
- Blog detail: `GetPublishedBlogPost` applies the SAME public filter as the list and returns `ErrNotFound` for unknown ids and non-public rows alike — masking lives in the query, callers must not disambiguate. The creator comes from a LEFT JOIN (`users` may be gone — ON DELETE SET NULL); download rows come from a second query `ORDER BY position, id` (id is the stable arbitrary tie-breaker). The download readers return nil for no rows; the handlers own the non-nil empty-slice projection so the wire emits `[]`.
- Projects: `ListPublishedProjects`/`GetPublishedProject` are the blog readers' counterparts over the same shared bodies (same keyset tuple, same `status='published' AND published_at_ms IS NOT NULL` filter, same masked `ErrNotFound`). The continuation tuple is the shared `PageKey` (`keyset.go` — the rule-of-three collapse: one shape serves every collection). `UserRef` is the one user projection on content. Downloads join `ORDER BY position, id`; the wire `name` maps the batch-entry label (no `resolution` concept on projects).
- Search: `search_store.go` owns the FTS5 index maintenance — `IndexBlogPostTx`/`IndexProjectTx`/`DeleteBlogPostTx`/`DeleteProjectTx` run INSIDE the caller's transaction (the import tool and the content-administration stores) and `ReindexAll` is the rebuild/backfill path (`make rebuild-search-local`). Index only rows with a publish time; the query-time filter `status='published' AND published_at_ms IS NOT NULL` is the visibility authority (defense in depth). `SearchContent` builds one FTS branch per included content type (MATCH cannot use a table alias — the FTS tables are referenced by real name, only the content tables are aliased), UNION ALLs them, and applies the merged keyset predicate — a cursor is only meaningful with the same q+type+sort+window. The merged projection carries the display `Subtitle`: the blog branch selects `p.subtitle`, the project branch an aliased empty string, so both branches scan the same shape. The match argument is a bound parameter, never interpolated. Index text is normalized Greek (internal/search) — do not index raw text or switch to pure-SQL rebuilds. **Title sort:** `SearchSort` selects the ordering and `SearchKeyset` the continuation tuple — the newest-first date sort reads `PublishedAtMS` + `id` (`published_at_ms DESC, id ASC`), the oldest-first sort mirrors it (`published_at_ms ASC, id ASC`, continuation strictly newer), the title sort reads `TitleKey` + `id` and orders/continues with `title COLLATE sf_greek` (the collation name is a `internal/search` package constant — never user input; the keyset values stay bound parameters). The title sort truncates nothing itself: the handler mints `TitleKey` with `search.SortKey`, whose folding invariance is what lets the predicate compare raw titles against it. The title-sort key is mutable: a title edit between page reads can move a row across the cursor boundary (a skip or a repeat) — the hearts top-sort caveat's sibling, accepted for the same reason. **Window:** `SearchContent` takes one `SearchQuery` (match, scope, sort, `SinceMS`, `UntilMS`, limit, keyset) instead of a positional list; `SinceMS` is inclusive and `UntilMS` exclusive, both nil when unbounded (pointers, not a zero sentinel — 1970-01-01 is a legal bound whose value is 0), and both are bound parameters layered onto the union as ordinary conditions — the handler converts calendar days, so no date string reaches SQL.
- Favorites: `favorite_store.go` owns the two join tables behind `AddFavorite`/`RemoveFavorite`/`FavoriteStatus`/`ListFavorites(ctx, db, k, …)`. The add path is conditional `INSERT…SELECT WHERE EXISTS` on the PUBLISHED content — the check and the write share one statement (no TOCTOU), a repeat favorite hits the composite PK (idempotent), a 0-row insert is `ErrNotFound` (masked), and a FK violation (user deleted mid-request) also maps to `ErrNotFound`. `isForeignKeyViolation` is the FK twin of `IsUniqueViolation` (driver-text discriminator, canary-pinned in `favorite_store_test.go`). Lists reuse the two-shape keyset pattern with the tuple `(created_at_ms, content_id)` via `FavoritePageKey` — the sort is the FAVORITING time, not the publish time. The status read is two `EXISTS` subqueries in one row (published, favorited) — the handler masks non-published ids with the same 404 as the content detail. The shared list projection's subtitle slot mirrors the search union: the kind whose `ownColumn` is a subtitle selects it, projects an empty string, so both kinds scan one shape. `deleteContentFavoritesTx` is the content lifecycle's in-tx cleanup (leaving published, or a delete).
- **Content kinds (docs/patterns/go/content-kinds.md):** every per-content-type storage name lives on one `ContentKind` descriptor (`content_kinds.go`); readers take the descriptor, the write transactions stay per kind, and `TestContentKindTablesConfined` keeps the table-name literals confined to the descriptor file. `allContentKinds` is the sweep order for the readers that must cover every kind (the media reference set, the metrics sums, the search-index clear, the notification title joins).
- **Content administration:** `staff_content.go` owns the staff reads. The draft-visibility gate (`staffGateClause`, built from `roleWeightCase` — the draft gate's SQL mirror of `identity.RoleWeight`, pinned by the role-matrix test; the feed's visibility predicate carries its own `targetRoleWeightCase` mirror, whose unknown-role arm deliberately weighs above every staff role) lives IN the read queries; `StaffContentFilter`/`writeTitleFilter` narrow the list (status exact, title folded per word). Create/update/delete are the per-kind transactions in `blog_admin_store.go`/`project_admin_store.go`: create indexes the FTS row atomically when published; update replaces the FTS entry (delete-then-insert, stamp-based membership: an ARCHIVED row keeps its stamp and its index row), deletes favorites when leaving published, and stamps `published_at_ms` on the FIRST transition into published (preserved afterwards); delete removes the FTS row before the hard-delete (downloads/favorites cascade via FK). Revision guards: `UPDATE/DELETE … WHERE revision = ?` — 0 rows after the disambiguation SELECT = `ErrConflict` (the documented benign TOCTOU — keep the comment when copying the pattern). The ungated read-back serves the WRITE paths only — never expose it to request handling.
- **Staff content list filters:** `ListStaffBlogPosts`/`ListStaffProjects` take a `StaffContentFilter{Status, Query}` — an exact status and, for the title, one `instr(search.FunctionFold(title), ?) > 0` per query word through the shared `writeTitleFilter` helper (staff_content.go). `search.FilterTokens` does the split and `Fold` the folding, so `dr stone` finds `Dr. Stone` at the same word boundaries the public search uses (the two rules still differ: reserved words, the substring-vs-prefix rule, and the no-word query); a query with no words adds no clause at all (the `instr(x, '')` guard). Both fields are optional, an empty one means no filter, and neither touches the ordering or the keyset tuple, so a cursor stays a valid position under a different filter (the page's URL is what binds the two). The list queries are built from ONE WHERE clause (gate, then filters, then the keyset predicate, with their bound arguments in that order) — the `ListStaffUsers` idiom.
- Projects administration: `project_admin_store.go` is the blog store's counterpart — same transactions, same gate, same revision guards, plus the slug contract. The UNIQUE constraint on `projects.slug` is the race-free backstop: a slug collision surfaces as `ErrSlugTaken` (narrowed by `isSlugTakenViolation` — only the slug constraint, never the primary key), the create handler retries with collision suffixes and the update handler maps it to 422 `{slug, alreadyTaken}`. The draft-visibility gate reuses the same `staffGateClause`.
- Downloads: download rows join the content write transactions — `insertContentDownloadsTx` (create) and `replaceContentDownloadsTx` (update: DELETE + reinsert AFTER the revision-guarded UPDATE matched, so a stale revision rolls the download swap back with the content write). Row identity: fresh `id.New` ids, `position` = array index, `created_at_ms` = the CONTENT row's created_at_ms (the import precedent — `internal/migration/import.go` stamps rows the same way; the update's now must NOT reach these rows). The staff reads carry the rows VERBATIM via the shared `listContentDownloads` (no link guard — the public reads keep theirs); `store.Download.Label` maps the kind's label column (`downloadLabel`: `resolution` or `name`).
- Staff-detail NULL discipline: the staff scans in `staff_content.go` read the raw `creator_id`/`updater_id` columns through `nullStringValue` (the read half of the `null.go` family) — migrated rows carry NULL ids (the import never stamps them) and `ON DELETE SET NULL` keeps them coming, so scanning NULL into a plain string is a Scan error that 500s the admin form. The user-ref tail reads through `userRefTail`, whose `ref()` answers nil for a NULL id; `database/sql` takes ONE Scan call per row, so the tail's destinations join the row's in that call. Every nullable column must scan into a NullString/pointer target; the staff-detail regression tests (`TestStaff*_NullCreatorUpdater`, `TestUpdate*_MigratedRow`) pin the shape.
- Media references: `media_store.go` owns the reference-set contract — `ReferencedMediaPaths` (the sweep's snapshot: `blog_posts.thumbnail_url` ∪ `projects.thumbnail_url` ∪ `users.avatar_url`, UNION-deduped, the avatar leg NULL-filtered; legacy absolute URLs are harmless set members) and `MediaPathReferenced` (the explicit-delete guard's point lookup — all three columns). Membership means KEEP — one file can back several rows (the media import dedupes identical bytes across posts), so lifecycle checks always span ALL rows, never the single row being touched. Any NEW media-referencing column must join BOTH functions and the sweep's grammar or referenced files get deleted.
- Staff user list: `user_admin_store.go` owns `ListStaffUsers` — keyset over the per-store `UserPageKey{CreatedAtMS, ID}` (`created_at_ms DESC, id ASC` — the honestly-named tuple, the `AdminPageKey`/`FavoritePageKey` precedent; the shared codec's payload stays structurally identical). Optional role/status filters. Two optional filters + the continuation predicate make four query shapes, so a small WHERE builder (bound params only) replaces the blog list's two-shape split — the builder comment explains why. Email is ALWAYS selected and the handler decides whether the viewer's role may see it (admin+ only) — the store stays free of a caller-dependent projection. `UpdatedAtMS` is deliberately NOT in the projection — no consumer needed it. `AvatarURL *string` is there for the same reason email is: it is the STORED storage-form reference (NULL → nil through `nullStringPtr`, the blog-store creator-ref idiom), the store stays URL-free, and the handler projects the absolute served form — but unlike email it is NOT role-gated.
- Durable audit: `audit_store.go` owns `AuditWriter` — the store half of the dual-write trail (implements `audit.Writer`; `cmd/api` registers it). It stamps `created_at_ms` from its own `Now` clock (never a schema default) and generates row IDs via `id.New`. Empty actor/target/target_role strings persist as SQL NULL (`nullableString`, the write half of the `null.go` family). `ListAuditEvents` is the super-admin browser's read: a bounded TAIL — `created_at_ms DESC, id DESC`, an optional exact-event filter built with the `ListStaffUsers` WHERE-builder shape, and `nullStringValue` decoding the nullable identities back to empty strings so the handler can omit them. `idx_audit_events_created` serves the ordering, and the filter — which the wire contract restricts to the accepted kinds — scans the newest rows and stops at the limit.
- Password reset: `user_password_store.go` owns `ResetUserPassword` — one transaction replacing the verifier, setting `must_change_password = 1`, bumping auth_version, and deleting the target's sessions. NO auth_version CAS (an admin reset must work on accounts with unusable verifiers); the bump is revocation, not a race guard. `UpdatePasswordAndRevokeSessions` clears the flag (`must_change_password = 0`) in the same transaction — the forced change is the gate's way out. `SessionByDigest` projects `u.must_change_password` onto `SessionUser` so the forced-change middleware needs no extra query.
- Role change + deletion: `user_admin_write_store.go` owns `ChangeUserRole` (role + auth_version bump + session delete in one transaction) and `DeleteUser` (hard delete in ONE transaction: it first decrements every comment the account hearted, per content kind, for the heart rows the delete is about to cascade away — the account's own comments are decremented too and then cascade with them, harmlessly — the counter/source agreement; then the FKs cascade every row the account owns — favorites, sessions, comments and their replies, follows, notification rows and read state, reset/verification tokens, push subscriptions and preferences — and SET NULL creators/updaters plus the account's actor reference on other recipients' notification rows, so authored blog/project rows survive). Both run the last-active-super-admin guard INSIDE the transaction via the shared `guardLastActiveSuperAdminTx` helper: SELECT the target's role/status, then each caller passes its own trigger condition (demotion of an ACTIVE super-admin; deletion of one) — the helper COUNTs the active super-admins and `<= 1` returns the `ErrLastActiveSuperAdmin` sentinel (a SUSPENDED super-admin is outside the active count, so operations on them never trigger it). No auth_version CAS (user-management operations let the winner apply; the bump is revocation). The handler short-circuits the same-role no-op before the store call — `ChangeUserRole` assumes the roles differ.
- Suspend/reactivate: `user_admin_write_store.go` owns `SuspendUser` (status='suspended' + bump + session delete in ONE transaction — the "same transaction" rule; the guard runs inside with `wouldReduce` = target is an ACTIVE super-admin, so self-suspension of the last active super-admin is the guarded 409) and `ReactivateUser` (status='active' + bump in ONE atomic UPDATE — no session delete, suspension already removed them; no guard, reactivation cannot reduce the active set; no transaction needed, a single statement is already atomic). Both stamp `updated_at_ms`. Suspension suppresses delivery (the emitters and the send-time check skip a non-active recipient) but RETAINS the target's push subscriptions and preferences; reactivation resumes delivery. The handler short-circuits the same-status no-op before the store call. (There is no standalone `IncrementAuthVersion`.)
- Avatar write: `user_store.go` owns `UpdateUserAvatar` — one statement setting `avatar_url` + `updated_at_ms` by id, NO auth_version bump (an avatar change is not a revocation event), 0 rows → `ErrNotFound` (the deletion race maps to the handler's generic 401).
- Lenient username lookup: `user_store.go` owns `UserByCanonicalLenient` — the sign-in bridge for imported usernames whose legacy whitespace a form cannot reproduce (a leading, trailing, or doubled run). The SQL prefilter is a coarse superset (every Unicode whitespace rune stripped); `NormalizeCanonWhitespace` (lowercase + `strings.Fields` collapse, exported) is the authority and also the identifier-key rule for the sign-in and forgot-password rate limiters, so spelling variants share one bucket. The exact row wins wherever the cursor delivers it; a lone normalized match answers; two rows normalizing alike wrap `ErrNotFound` and set `IsAmbiguousUser`, so registration refuses the name as `ErrUsernameTaken` instead of minting a third near-duplicate (concurrent variants still collide on the UNIQUE `username_canon`), and every other miss is a plain `ErrNotFound`. Writes and display keep the original spelling; registration accepts single inner spaces under the same fold. `UserRefByCanonical` is the narrow reader behind the public byline projection (id, username, stored avatar reference; `ErrNotFound` when absent).
- Notifications feed: `notification_store.go` owns the two-source feed — the five role-weighted audit events (staff only) UNIONed with the viewer's `user_notifications` rows under ONE ordering (created_at_ms DESC, id ASC) and one cursor tuple; the union branches carry explicit column aliases (the outer keyset predicate addresses them). **The user half carries the draft re-gate:** below the staff floor the `draft_activity` kind leaves the branch entirely, and at the floor it is served only when the CURRENT content row's creator is the viewer or weighs strictly below the viewer's (`userNotificationsFrom` — the draft gate's rule evaluated at READ time, so a role change can withdraw a delivered notice); the one source backs the list, the count, and the unread badge. `feedEventsClause` is BUILT from the audit package's event-name constants (single source — never hardcode the five names); `targetRoleWeightCase` mirrors `identity.RoleWeight` for the four accepted roles and weighs ANY non-NULL unknown role at 4 (above every staff role) so it can never leak — pinned against the model by `TestNotificationVisibilityMatrix` (the draft-gate canary precedent — a weight change must update both). The shared `visibilityPredicate` is the whole staff-half authorization: five events + `target_role IS NOT NULL` + snapshot weight ≤ the viewer's (bound parameter) — no users JOIN for authorization, so deleted targets keep visibility and role changes never rewrite history. Unread sums both sources (audit anti-join + the gated user branch's unread rows); `MarkNotificationRead` walks BOTH id spaces with per-space authorization (a recipient-scoped UPDATE first — a foreign/unknown user row affects 0 rows and falls through to the audit space — then the visibility-scoped audit existence check + `INSERT OR IGNORE`); unknown and invisible ids are the SAME `ErrNotFound`, and the below-floor user space excludes the re-gated draft kind from mark-read, mark-all, and every delete path exactly as the read does (a staff viewer in the gate's band may still mark its own hidden row — no content is served). `MarkAllNotificationsRead` is the recipient-scoped UPDATE plus the staff `INSERT OR IGNORE … SELECT`; both writes absorb repeats. `NotificationPageKey{CreatedAtMS, ID}` is the honestly-named tuple (the timestamp slot carries the entry's created_at_ms across both sources). **Read state:** every returned item carries `Read` — the audit branch answers it with an `EXISTS` on `notification_reads` (bound BEFORE the visibility weight, because it sits in the SELECT list) and the user branch with `un.read_at_ms IS NOT NULL`; both branches append `is_read` as their LAST column so the UNION stays aligned, and it is scanned as an int (SQLite returns integer booleans) then narrowed to `bool`. `DeleteNotification` removes one feed entry: a recipient-scoped user row, or a per-viewer dismissal of a visible audit event (`dismissed_at_ms`, the ledger row untouched); `DeleteReadNotifications` removes the viewer's READ rows only (`read_at_ms IS NOT NULL`), so a bulk action can never discard something unread; `DeleteAllNotifications` sweeps both halves in one transaction. Dismissed audit events leave the list, the count, and the badge — the read branches, the mark-read guard, and mark-all all exclude them — and the audit ledger is never deleted by any of them. The delete surface lives in `notification_delete_store.go`.
- Comments: `comment_store.go` owns the thread reads, with the writes in `comment_write_store.go`, the inline reply window in `comment_reply_store.go`, and the heart toggle in `comment_heart_store.go`. One implementation behind the `ContentKind` descriptor (names are package constants — the content-kinds pattern), and the exported readers take it: `ListComments`/`ListCommentsFocus`/`ListCommentReplies`/`CommentCount`/`CreateComment`/`CreateCommentReply`/`UpdateComment`/`CommentAuthorID`/`DeleteComment`/`SetCommentHeart`. `authorStaffRoleCase` mirrors `identity.CanViewStaffList` (moderator+): it returns the ROLE for staff authors and NULL otherwise, and `IsStaff` is derived from it (`StaffRole != ""`) so the staff set is listed once — pinned by `TestAuthorStaffRoleMirrorsModel` (a non-staff author's role never leaves SQL). All three sort tuples live in `commentOrder`/`commentContinuation`/`commentRankPredicate` (top carries the hearts slot; the time sorts do not — the handler mints `h=0` for them); the focus window is `offset = (rank-1)/limit*limit` over `commentRankPredicate`'s COUNT (fixed window, not anchor-centered), with the anchor = the target or its parent and deleted anchors falling back to page 1. The published gate (`requirePublishedContent`) precedes every primary read (the PAGE count readers `CountTopLevelComments`/`CountReplies` deliberately skip it per `docs/patterns/go/collections.md` rule 3; `CommentCount` applies it — the count endpoint's draft case is the masked 404); writes use the `INSERT … SELECT WHERE EXISTS` pattern (create) or the in-tx gate checks (reply/update/heart) — DELETE is the one exempt path (the handler authorizes, then `DeleteComment` reads the author + content in-tx before deleting by id); `CommentAuthorID` returns the author AND the content's published flag, so the handler can answer the masked 404 to a non-author below the staff floor on unpublished content. `CreateCommentReply` runs in ONE transaction: the parent lookup is CONTENT-scoped (unknown/foreign → ErrNotFound — a foreign reply-parent never leaks its depth), same-content reply → `ErrInvalidParent`, then the gate'd INSERT and the `comment_reply` row (self-replies suppressed) — a notification failure fails the reply (atomic). The heart toggle is one transaction (row insert/delete + conditional counter delta — no drift); a freshly inserted heart also emits the `heart` notification row to the comment author, skipped for a suspended author (the active-recipient rule; the hearted comment is the deep-link target; idempotent repeats emit nothing), an unheart removes that row, so an unheart never leaves a stale notice. A comment hard-delete or an account deletion deliberately does NOT rewrite notices — `user_notifications.comment_id` dangles by design: a hard-deleted comment's deep link falls back to the deleted-target notice, and a deleted actor renders as the system label (the rendering lives in `web/src/features/comments/AGENTS.md` and `web/src/features/notifications/AGENTS.md`). A self-heart returns `ErrSelfHeart` BEFORE the write — the DELETE path skips only the self-ban, while the published gate applies in both directions, so an existing self-heart can still be unhearted on published content; FK violations map to `ErrNotFound` (the favorites `isForeignKeyViolation` precedent). Sentinels: `ErrNotAuthor` (403), `ErrInvalidParent` (422), `ErrSelfHeart` (422). **Comment fan-out:** `CreateComment` returns `([]NotificationEvent, error)` — after the gate'd INSERT lands it selects the content title in-tx and emits ONE `comment` row per follower (author excluded) with a fresh `id.New` per row; the events are the push fan-out input (pinned by `notification_emission_test.go`). **Reply window:** `attachReplies` sets each item's `ReplyCount` (one GROUP BY), then fetches at most `inlineReplyWindow` (=3) replies per parent, with `HasMoreReplies` as the reader's continuation signal (the HANDLER mints the cursor from the window's last reply — the store never knows the namespace). The bound is a `ROW_NUMBER() OVER (PARTITION BY parent_id …)` subquery; a focus anchor whose parent is on the page shifts THAT parent's window to its fixed page (`replyFocusOffset` computes `(rank-1)/3*3`, and the shifted parent is fetched separately with LIMIT/OFFSET). `ListCommentReplies` is the replies operation's reader: published gate + a parent gate (`parent_id IS NULL` — a reply-as-parent is the masked `ErrNotFound`), ascending `(created_at_ms, id)` keyset. Cost note: without a `(parent_id, created_at_ms, id)` index the rank subquery still scans a parent's replies — no new index ships. Depth note: the FK permits arbitrary nesting and depth 1 is an API rule — a hand-written row whose parent is itself a reply is invisible to every thread read but still counted by `CommentCount` and the content indicator subqueries (`content_kinds.go`). **Removal notice:** `DeleteComment` is a TRANSACTION returning `(NotificationEvent, bool, error)`: it reads the author + content id + content title in-tx (the row is about to vanish), deletes (FK-cascading replies and hearts), and — only when `authorID != actorID` — inserts ONE `comment_removed` row whose `actor_id` is NULL by design (the notice is actorless; the audit ledger holds the actor). A cascade-swept reply emits nothing. `notificationID` is handler-minted (the single-recipient precedent), unused on a self-delete.
- Follows: `follow_store.go` owns `content_follows` — the favorites mirror behind `FollowStatus`/`AddFollow`/`RemoveFollow(ctx, db, k, …)` (conditional INSERT…SELECT WHERE EXISTS on the PUBLISHED content, composite-PK idempotency, two-EXISTS status read, `ErrNotFound` for the masked outcomes). The content_kind value is bound, not spliced. No follow LIST function (no surface exists).
- Self-service session list: `session_list_store.go` owns `ListSessions` (window `expires_at_ms > nowMS` — the expiry filter is IN the query, so an expired row is absent before cleanup runs; order `created_at_ms DESC, id ASC` with the `SessionPageKey` tuple and the two-shape keyset pattern; `client_label` scans through `sql.NullString` into an empty `SessionListItem.ClientLabel`) and `CountSessions` (the same window), while `session_store.go` keeps the session-creating writes and `RevokeSession` (`DELETE … WHERE id = ? AND user_id = ?` — the owner predicate IS the authorization boundary, so a foreign id deletes nothing; the count reports whether a row went, and the handler answers the same idempotent 204 either way, never bumping `auth_version`). `nullableString` maps the empty label to SQL NULL. The session-creating params (`CreateSession`, `RehashPasswordAndCreateSession`, `CreateUserAndSession`) all carry `ClientLabel` — the classifier output, empty meaning NULL.
- content_updated emission: `UpdateBlogPost`/`UpdateProject` return `([]NotificationEvent, error)` as a third value. **Active-recipient rule (every emission bullet below):** each emitter selects `status = 'active'` recipients only — suspension revokes the outbound channel as well as sessions — and the single-recipient reply/heart/removal paths check the recipient's status in their own lookup; the write always lands, only the notice is suppressed. The emission gate is `curStatus == 'published' && p.Status == 'published'` — followers minus the editor get one `content_updated` row (comment_id NULL) each, in the update transaction; draft edits and unpublishes emit nothing. The events carry the NEW title. `notifyFollowersTx` takes the content's `ContentKind` and binds its kind value.
- new_content broadcast: `CreateBlogPost`/`CreateProject` also return `([]NotificationEvent, error)` — a create AS PUBLISHED broadcasts one `new_content` row per opted-in recipient (the creator excluded, in-tx). `UpdateBlogPost`/`UpdateProject` emit the same broadcast when the row transitions INTO published WITHOUT a prior publish stamp (`!curPub.Valid && p.Status == 'published'` — the publish stamp is the gate, not the status string); re-publishes emit nothing. Recipients = the EFFECTIVE `new_content` preference: explicit `push_enabled = 1` row, else the role default (moderator+ on — `staffRoleClause` mirrors `identity.RoleWeight`, pinned by `TestNewContentBroadcastRoleDefaultsMirrorModel`). The preference gates BOTH the in-app row and push for this broadcast kind (no follow gate exists).
- Draft-activity notice: `notifyDraftActivityTx` (notification_emit_store.go) is the STAFF-ONLY emitter for writes that leave content unpublished — create-as-draft (`created`), a non-published edit (`updated`), and leaving published (`unpublished`, draft OR archived). It is the inverse of the broadcast on the preference axis: the recipient set is the draft-visibility gate (the row's creator, or a role weight STRICTLY above the creator's — the same comparison the staff reads use, built from `roleWeightCase`), minus the actor, restricted to the staff floor (the gate's `-1` arm would otherwise admit a plain user on an unattributed row) and to EXPLICIT opt-ins — there is NO role default for this kind. The content table comes from the caller's `ContentKind`, so the emitters never see a kind string. `draft_action` is written per row and bound to the kind by the migration's iff CHECK; the emitter's action constants are its only writers. The feed and the service worker both REFUSE an unknown action rather than guessing a verb (no item, no notification).
- Follower fan-out helper: `notifyFollowersTx` (notification_emit_store.go) is the shared `comment`/`content_updated` emitter — the rule-of-three extraction, the Tx-helper precedent (caller owns the tx, the store owns the SQL). It mints one notification id PER ROW inside the store (`id.New`) — the DELIBERATE seam split: the single-recipient reply/heart paths keep the handler-minted `notificationID` seam, a multi-recipient fan-out cannot mint its unbounded id count at the handler layer. A follower row read in the same tx cannot vanish before its insert (immediate lock) — no FK race mapping exists in the helper. `notifyNewContentTx` is the broadcast sibling: same id-minting seam, recipient rows come from the preference/role query in the same tx. Both take the content's `ContentKind`.
- Reset tokens (`password_reset_store.go`): `ResetPasswordWithToken` order is SELECT token → CAS UPDATE users (`auth_version` + `status='active'` — the CAS is the single-use gate under the immediate tx, not the DELETE) → digest-scoped DELETE + `RowsAffected==1` assert + session cleanup. The REJECTED path (suspended/version-mismatch) commits the digest-scoped token deletion ALONE — a rejection still kills the link and never kills a fresher token minted meanwhile. `CreateResetToken` = delete-then-insert (one active per user; UNIQUE(user_id) is the schema backstop). `UpdatePasswordAndRevokeSessions` + `ResetUserPassword` delete token rows in their txs — ANY password change kills in-flight links. The reset UPDATE stamps `email_verified_at_ms = COALESCE(email_verified_at_ms, ?)` (the self-service reset proves inbox control; the admin reset does NOT stamp).
- Verification tokens (`verification_store.go`): the reset-token shape with its own sentinel — `CreateVerificationToken` (delete-then-insert), `VerificationTokenUserID` (advisory read), `VerifyEmail` (SELECT token → conditional stamp `UPDATE … WHERE status='active' AND email_verified_at_ms IS NULL` → success path: digest-scoped DELETE + `RowsAffected==1`; zero-row stamp disambiguates gone/suspended (kill + generic invalid) from already-verified (consume + success — idempotent)), `DeleteExpiredVerificationTokens` (the bounded batch). `user_store.go`'s `ChangeUserEmail` does the CAS swap + stamp reset + BOTH token-table deletes in one tx; existing sessions survive by design — no `auth_version` bump, because the caller re-authenticated with the current password (the CAS guard is race protection, not revocation). `users.email_verified_at_ms` (NULLable) joins the three `scanUser` SELECTs; `identity.User.EmailVerifiedAtMS *int64`.
- Web push: `push_store.go` owns the subscription + preference persistence. `UpsertPushSubscription` reassigns a foreign-user endpoint BEFORE the insert (one tx; the device's newest login owns the endpoint) and returns the STORED id (a resubscribe keeps the existing row id). Preferences follow absence = the caller's role default (`EffectiveNotificationPreferences`/`EffectivePushEnabled`) — a row is an explicit override. `NotificationEvent` (the comments' fan-out return) deliberately carries NO actor field — the handler already holds the session user, so an actor field would be a dead column. `comment_heart_store.go`'s `SetCommentHeart` and `comment_write_store.go`'s `CreateCommentReply` return `(NotificationEvent, bool, error)` — the event only when the notification row actually landed (idempotent repeats emit nothing).
- Dashboard metrics: `metrics_store.go` owns the two read-only aggregate readers — `GetMetricsTotals` (users GROUP BY role+status, each content table GROUP BY status via its `ContentKind`, and the two cross-kind sums built from `allContentKinds`) and `GetMetricsActivity(ctx, db, sinceMS)` (registrations from `users.created_at_ms`, DISTINCT `sign_in_success` actors, sign_in_failure count, and one grouped `event IN (…)` read). Nothing writes and nothing is stored: no counters, no summary table, no migration. Three rules worth keeping: **change counts are `result = 'success'` only** — a blocked 403 or a failed write is not activity (only `sign_in_failure` counts its failures, because the event name IS the failure signal); **the window boundary is the caller's `sinceMS`, inclusive**, so the handler computes one instant and both the SQL and the echoed `since` come from it; and **the two readers are deliberately separate statements** — each value is an exact live read, but one response is not a snapshot (no read-only transaction spans them; the bounded skew is accepted). Content-status literals (`published`/`draft`/`archived`) match the 0003/0004 CHECKs, like the rest of the store.
- **Public visibility is one rule, repeated per query shape.** `status = 'published' AND published_at_ms IS NOT NULL` appears in every public content reader (detail, lists, comments, hearts, favorites, follows, and search) in alias-free and `p.`-qualified forms; the copies are identical today, and a change to the rule must sweep all of them. The staff gate is a DIFFERENT rule (the draft-visibility gate in `staff_content.go`), not a copy. The in-file pair in `content_kinds.go` composes from `publicPredicate` so at least that pair cannot drift.
- **Accepted query shapes (planner evidence on seeded data):** the audit tail scans `idx_audit_events_created` and sorts the returned window for the `id` tie-break; the staff user list and the staff content list sort with a temp B-tree (their tables stay at staff-page scale, so no ordering index is warranted); the notifications feed does the same over its per-viewer result set; the public blog/project lists and search use their published/keyset indexes. Project slug lookups are served by the UNIQUE auto-index. Add an index only with a plan that shows a scan dominating.
