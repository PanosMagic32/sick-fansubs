# internal/routes — Agent Navigation

Route registration and chain composition: each domain exports a registration function taking the mux plus concrete dependencies, so `main` stays wiring-free. The chain shapes and their order are [`docs/patterns/go/route-chains.md`](../../docs/patterns/go/route-chains.md).

## Open this file when

- adding/removing endpoints, changing middleware chains, or touching the `/api/v1` fallback.

## Folder-local conventions

- `chains.go` is the only file that composes middleware — every namespace names a chain from that file, and the `internal/codestyle` guard keeps it that way. The wire contract and the route table are pinned together by `TestOpenAPIRoutesMatchRegistrations` (`openapi_parity_test.go`): every documented operation dispatches to a registered pattern and every method-prefixed registration is documented (method-less JSON-404 fallbacks, subtree mounts, and the `/media/images/{file}` asset path excepted). `Health` (health.go) is special only in what it skips: it takes `publicChain` (RequestID alone), so probes keep their server-generated ID without any session/origin work (`internal/routes/health_test.go` pins it).
- Blog: `blog.go` registers the exact collection path and the `{id}` wildcard detail path side by side — Go ServeMux precedence gives the exact pattern the win; the wildcard matches exactly one non-empty segment, so `/api/v1/blog-posts/` still falls to the catch-all. Both blog endpoints use `publicChain` (public GETs). `POST /api/v1/blog-posts` + `PUT/DELETE /api/v1/blog-posts/{id}` carry `authenticatedChain` (method-aware registration per pattern — the public GETs keep the public chain), and the staff reads register at `GET /api/v1/admin/blog-posts[/{id}]` with the same chain. `Blog()` takes `(mux, db, dataDir, secure, trustedOrigin, publicBaseURL, notify push.Notifier)`. Unknown `/api/v1/admin*` paths hit the JSON 404 fallbacks — never the SPA HTML.
- Projects: `project.go` mirrors the blog registration (`/api/v1/projects` + `/api/v1/projects/{id}`, both on `publicChain`). The registration test's "unregistered subpath" list intentionally includes well-shaped unknown ids — those exercise the detail handler's masked 404, not the catch-all; both outcomes are the same JSON 404.
- Unknown `/api/v1/*` paths must return the JSON 404 problem (`APIFallback` + the auth sub-mux catch-all) — never the SPA HTML. Every namespace fallback registers through the shared `notFound()` helper, which applies `publicChain`, so an unmatched path still carries the `X-Request-ID` header and the problem's `requestId` (`internal/routes/api_test.go` pins it).
- Media routes live outside `/api/v1` (`media.go`): `GET /media/images/{file}` plus `/media`/`/media/` fallbacks — every non-serving media path is a 404 problem, never SPA HTML. Non-GET media requests fall to the subtree fallback (404), which is the accepted behavior. Literal `..` segments get the ServeMux path-cleaning redirect before the 404 fallback — that redirect is expected, do not "fix" it.
- Media upload: `POST /api/v1/media` is registered with `authenticatedChain` (the upload path; the explicit delete below is the namespace's other path). The method-less `/api/v1/media` pattern follows it and answers NotFound for every non-POST method — without it the method-aware ServeMux would 405 in text/plain, breaking the JSON-only API rule. `Media()` takes `(mux, dataDir, db, secure, trustedOrigin, publicBaseURL)`.
- Media explicit delete: `DELETE /api/v1/media/{file}` joins the upload on `authenticatedChain`; the method-less `/api/v1/media` catch-all now answers NotFound for every non-POST/DELETE method on the bare path, while non-DELETE methods on `/api/v1/media/{file}` fall to the `/api/v1/` JSON 404 catch-all.
- Users: `users.go` registers the profile (`GET /api/v1/users/me`) and the eight favorites paths (`GET/PUT/DELETE /me/favorites/{blog-posts,projects}[/{id}]`) behind `authenticatedChain` — CSRF joined the chain with the favorites mutations (it only validates unsafe methods, so the GETs pass through untouched). `Users()` takes `publicBaseURL` for the favorites lists' absolute thumbnail URLs and `dataDir` for the avatar upload. Both `/api/v1/users` (exact) and `/api/v1/users/` (subtree) are registered so the bare namespace root also gets the JSON 404. Staff user-management paths belong to this subtree — do not pre-register them.
- Avatar upload: `PUT /me/avatar` registers inside the users subtree (strip-prefixed) on `authenticatedChain` — ANY authenticated user (no role floor; the handler enforces self-service by construction: the session's user id IS the row written). The chain includes ForcePasswordChange, so a flagged account cannot upload before changing its password. A PUT to `/me/avatar` on an unauthenticated request is the handler's generic 401 (Session passes unauthenticated requests through); unknown paths in the subtree stay the JSON 404.
- Staff user list: `GET /api/v1/users` (the BARE namespace root — the blog-list precedent: collections address the bare path) is registered on `authenticatedChain`; the method-less exact `/api/v1/users` catch-all still answers every non-GET method with the JSON 404 (the method-aware mux's 405 text/plain never reaches the client). `Users()` hands `publicBaseURL` to the staff list and to the three write handlers whose response carries `avatarUrl` (role change, suspend, reactivate); `UserDelete` is a 204 with no projection.
- Password reset: `POST /api/v1/users/{id}/reset-password` registers inside the users subtree (strip-prefixed `POST /{id}/reset-password`) on `authenticatedChain` — the users subtree's chain includes `ForcePasswordChange`. A POST to `/me/reset-password` matches the wildcard with id `me` and answers the handler's masked 404 (the same JSON outcome as any unknown id).
- Role change + deletion: `PATCH /api/v1/users/{id}/role` and `DELETE /api/v1/users/{id}` register inside the users subtree (strip-prefixed `PATCH /{id}/role`, `DELETE /{id}`) on `authenticatedChain`. A PATCH/DELETE to `/me/role` or `/me` matches the wildcard with id `me` and answers the handler's masked 404 (the reset precedent).
- Suspend/reactivate: `POST /api/v1/users/{id}/suspend` and `POST /api/v1/users/{id}/reactivate` register inside the users subtree (strip-prefixed `POST /{id}/suspend`, `POST /{id}/reactivate`) on `authenticatedChain`. A POST to `/me/suspend` or `/me/reactivate` matches the wildcard with id `me` and answers the masked 404 (the reset precedent).
- Forced-change gate: `ForcePasswordChange` slots into `authenticatedReadsChain` and `authenticatedChain` (chains.go), and the users subtree uses the same constructor — after Session, before CSRF. The auth subtree's own chain (`authChain`) deliberately has NO gate: the whole subtree is the structural exemption.
- Notifications feed: `notifications.go` registers the SEVEN endpoints at the top-level mux (no subtree) — the two GETs on `authenticatedReadsChain` (RequestID → TrustedOrigin → Session → ForcePasswordChange, deliberately WITHOUT CSRF) and the five writes (`POST /{id}/read`, `POST /read-all`, `DELETE /{id}`, `POST /clear-read`, `POST /delete-all`) on `authenticatedChain`. Deletion covers both id spaces: an event row is deleted, a visible audit event is dismissed for the viewer (the ledger row itself survives). The forced-change gate applies to the whole surface (the every-non-exempt-path rule). The method-less exact `/api/v1/notifications` and the `/api/v1/notifications/` subtree both fall to the JSON 404 (the users precedent) — the method-aware mux's 405 text/plain never reaches the client.
- Comments: `comments.go` registers the eighteen paths (blog + projects mirror exactly) with a three-way chain split — the public list AND the replies page on `optionalSessionChain` (RequestID → TrustedOrigin → Session — deliberately WITHOUT CSRF and WITHOUT the forced-change gate: the read is public, a flagged user must still read comments), the count on `publicChain` (session-independent), and the six writes per content type on `authenticatedChain` (the forced-change gate applies to all comment writes). Method-less exact + subtree fallbacks for the `{commentId}` paths keep every other method/path in the namespace on the JSON 404 (the notifications precedent). **Rate limits:** `Comments` builds four user-keyed handler-level buckets (the pwChangeLimiter precedent) and hands the write handlers their buckets — create+reply share 10/15 min, edit 20/15 min, heart 15/5 min, delete 20/15 min, `429` + Retry-After. ONE instance per bucket is shared by both content kinds, so the budget is per user, not per segment.
- Self-service session list: `users.go` registers `GET /me/sessions` + `DELETE /me/sessions/{id}` on the users subtree chain (no new limiter — the favorites/follows deletion precedent). `handler.SessionsList` takes a nil-able clock; `handler.SessionRevoke` takes `secure` because revoking the CURRENT session clears the cookie after the commit. Both sit behind the forced-change gate like the rest of the subtree.
- Self-service reset: `auth.go` registers `POST /forgot-password` + `POST /reset-password` on the auth subtree's chain (NO forced-change gate — the subtree is the structural exemption, and `/auth/reset` is deliberately usable while flagged). Two new IP buckets (`forgotIPLimiter` 3/hour, `resetIPLimiter` 5/15min) ride `authChain`'s path-scoped slot like sign-in/register; the per-identifier forgot bucket is INJECTED into the handler (the signInIDLimiter precedent). `Auth()` now takes the mailer + `publicBaseURL` — the mailer is constructed in `cmd/api` (relay or the loopback-dev LogLink).
- Email verification + change: `auth.go` registers `POST /verify-email` (an IP bucket: `verifyIPLimiter` 5/15min) + `POST /resend-verification` (the SHARED verification-send bucket, injected into the handler). `users.go` registers `PUT /me/email` (handler `EmailChange`) — it receives the SAME shared limiter instance plus a SECOND `Service` carrying the real mailer (the admin-reset service keeps the nil-sender guard). `cmd/api` constructs the one `middleware.RateLimiter(1, 30min)` and passes it to BOTH `Auth()` and `Users()` — one verification email per user per 30 minutes across every surface.
- Route tests and local runs use the dev values (`secure=false`, `http://localhost:3000`); production wiring is config-driven in `cmd/api` (`APP_ENV=production` plus an explicit https `TRUSTED_ORIGIN`; `internal/config` fails closed).

- Web push: `push.go` registers the push endpoints. Reads (the two GETs) sit on `authenticatedReadsChain`; writes on `authenticatedChain`. No rate limits on the subscription/preference endpoints (the favorites precedent); the SELF-TEST send (`POST /api/v1/push-subscriptions/test`) is the exception — `Push` mints the ONE `middleware.RateLimiter(5, 10min)` instance for it (user-keyed, the pwChangeLimiter shape) and takes the `push.TestSender` seam (nil = delivery disabled). `Comments` takes the `push.Notifier` seam (nil = disabled dev path/tests) and passes it to the reply/heart/delete handlers, plus the comment-CREATE handler for the `comment` fan-out; `Blog`/`Projects` take it for their CREATE and UPDATE handlers — the `new_content` broadcast (create-as-published, and the update handlers' first-publish transition) and the `content_updated` fan-out. `Users` registers the six follow endpoints (`GET`/`PUT`/`DELETE /api/v1/users/me/follows/blog-posts|projects/{id}`) on the existing users subtree chain (no rate limits — the favorites precedent).
- Staff: `staff.go` opens the `/api/v1/staff` namespace with `GET /api/v1/staff/metrics`, `GET /api/v1/staff/logs` and `GET /api/v1/staff/audit-events` on `authenticatedChain` (the floors live in the handlers: `identity.CanViewMetrics` moderator+ for the metrics, `identity.CanViewLogs` super-admin for the logs and the ledger); no rate limit (the staff-list precedent). `Staff()` takes `logDir` — the resolved `data/logs` sink directory, not the data directory itself, since `internal/logging` owns the subdirectory name. The exact root and the subtree both register the JSON 404 (the users precedent).
