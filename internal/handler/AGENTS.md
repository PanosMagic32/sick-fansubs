# internal/handler — Agent Navigation

HTTP boundary: request parsing, status/headers, JSON and RFC 9457 problem writing, and the handlers for every feature surface (auth and health, blog, projects, comments, notifications, follows, search, media, push, and the staff dashboard's users, metrics, logs, and audit browser). No business rules, no SQL.

## Open this file when

- changing endpoint wire behavior, status codes, DTOs, cookie writing, or audit emissions.

## Folder-local conventions

- **Logging (docs/patterns/go/logging.md):** a handler obtains its logger with `logging.From(r.Context())` — the request-scoped logger `middleware.RequestID` installs — and never takes a logger parameter or calls a package-level `slog` function. Every 500 on a JSON endpoint goes through `writeInternalError(w, r, logger, "<subject> <action> failed", "error", err)`, which records once at the boundary and writes the generic problem. `media.go`'s plain-text 500 is the one recorded exception (it serves bytes) and logs through the same logger. `internal/codestyle` guards both rules.
- **Errors (docs/patterns/go/errors.md):** each domain package declares its sentinel vocabulary in one file (`internal/store/errors.go`, `internal/auth/errors.go`, `internal/search/errors.go`, `internal/media/errors.go`), and the handler's own body-classification sentinels live in `errors.go`. Store and auth responses map ONLY through the helpers there: `writeStoreError` (404 absence, 412 stale revision, 409 `/problems/auth/last-super-admin`, 403 non-author, 422 field violations), `writeStoreAccountError` (the same table, but a vanished VIEWER row answers the generic 401 — the session-outlives-user-row race), and `writeAuthError` (401 invalid credentials, 409 race, 422 taken fields, the two masked token problems, and `ErrValidation` with its `FieldError` extraction; the non-`FieldError` branch is defensive and answers `{general, invalid}`). The media and search vocabularies keep their own small writers (`writeProcessError`, the `search.ErrNoTokens` branch). Each helper RETURNS the status it wrote, so a caller that audits a failed attempt reads it (the wrong-password 401, the guard 409, the unmapped 500) instead of re-testing the error; the unmapped default is the masked 500, logged once by `writeInternalError`. `readJSONLimit` classifies decode failures through `classifyDecodeError` — typed checks first, plus the tree's ONE decode-error text match for `encoding/json`'s unknown-field message, pinned by `TestClassifyDecodeError_PinsTheLiveDecoder` and confined to that file by an `internal/codestyle` guard. The 429 and validation writers own their single records: callers pass their fields (`bucket`, `userId`) and never log the rejection themselves. Store sentinels are tested with `errors.Is`, never `==` (guarded).
- `readJSON` is read-then-parse under `http.MaxBytesReader` (4 KiB; charset parameters allowed) — do not reintroduce streaming decode. The whole body is buffered up to the bound per request, so peak memory scales with concurrency and no application-level concurrency cap exists (server-level only).
- The 422 wire shape is exactly `{field, code}` per violation — never internal validator `message` text.
- **Session guards:** a handler resolves its required session through `requireSession(w, r, logDetail)` (`session_guard.go`), which writes the generic 401 and returns false; `staffRequester` and `notificationsFloor` are the typed wrappers. Handlers never inline the `GetSession` + 401 block.
- Rate limiters must be non-nil: nil panics on the first rate-limited request.
- **Public-read throttling:** public reads are deliberately not rate-limited — no
  public-read throttling ships (a settled planning decision, not an open
  question). The only bounds are server-level; the public handlers' comments
  point here instead of restating a status.
- Cookie writes happen only after the store operation commits (`setSessionCookie` / `ClearSessionCookie`).
- Greek copy never lives here — the frontend catalog owns user-facing strings; this package returns stable identifiers only (root rule 9).
- **Collections (docs/patterns/go/collections.md):** `collection.go` owns the one envelope (`collection[T]`, `pageInfo`) and the one page builder (`writeKeysetPage`); `TestCollectionEnvelopeConfined` (internal/codestyle) confines them, and the items-only tails (`staffLogs`, `staffAuditEvents`) stay explicit. A caller parses with `parseKeysetParams`, then hands over a `keysetPage` whose `read` captures the parsed limit/cursor/filters, whose `count` closure must apply the SAME filters and scope as its `read` (it is the `pageInfo.total` source — a count that drops a filter is a wrong number), whose `item` projects ONE row, and whose `next` mints the continuation cursor; the envelope rules themselves live in the pattern doc.
- Cursor + list-param plumbing (rule-of-three): the keyset cursor contract lives ONCE in `cursor.go` — `"<prefix>" + base64url of {"v":1,"p":<publishedAtMs>,"i":<id>}`, max 256 chars — with the namespace prefixes `blogCursorPrefix`=`v1.`, `projectCursorPrefix`=`pv1.`, `searchCursorPrefix`=`sv1.`, `searchOldestCursorPrefix`=`so1.`, `blogFavCursorPrefix`=`fv1.`, `projectFavCursorPrefix`=`fpv1.`, `blogAdminCursorPrefix`=`av1.`, `projectAdminCursorPrefix`=`apv1.`, `staffUserCursorPrefix`=`uv1.`, `notificationCursorPrefix`=`nv1.`, `sessionCursorPrefix`=`ss1.` (the session list — the timestamp slot carries `created_at_ms`), and the comment namespaces `blogCommentCursorPrefix`=`bc1.` / `projectCommentCursorPrefix`=`pc1.` (decode checks the exact prefix, so cursors never cross endpoints; a cross-endpoint cursor is 400). The comment codec (`encodeCommentCursor`/`decodeCommentCursor`) is the codec EXTENSION: the payload `{"v":1,"s":<sort>,"p":<createdAtMs>,"h":<hearts>,"i":<id>}` is SORT-BOUND — decode requires `s` to equal the active sort, the time sorts require `h == 0`, and only the top sort carries the hearts slot. The top sort's key is mutable: a heart committed between page reads can move a row across the cursor boundary (a skip or repeat) — accepted; the two time sorts walk stable keys. The search title sort's key is mutable the same way: a title edit between page reads can move a row across the cursor boundary. The reply namespaces `blogReplyCursorPrefix`=`br1.` / `projectReplyCursorPrefix`=`pr1.` reuse the PLAIN name+id codec instead: the replies order is fixed (`created_at_ms`, `id` ascending), so there is no sort to bind. The title-sort codec (`encodeTitleCursor`/`decodeTitleCursor`) is the text-key sibling: namespace `searchTitleCursorPrefix`=`st1.`, payload `{"v":1,"k":<collation key>,"i":<id>}`, own bound `titleCursorMaxLen`=2048 (a key can be 800 UTF-8 bytes), and `validTitleKey` enforces ONLY the rune bound — an empty key and keys carrying control characters are legitimate mint output (a title of combining marks folds away, and titles are not stripped of control characters), so a stricter decoder would reject the server's own cursors mid-walk. Its namespace IS the sort binding (sv1./so1. for the two date directions, st1. for the title sort — each sort decodes only its own). Change format/version in `cursor.go` and OpenAPI together. Strict query params share `list_params.go`: `strictQueryParams` (url.ParseQuery on RawQuery — malformed is 400, `r.URL.Query` would silently drop bad pairs; unknown/duplicate names 400), `parseLimitParam` (outside 1..max — the endpoint's pair; keyset is default 20 / max 100, the tail reads declare their own — including int64 overflow — is 422 `{field:"limit", code:"outOfRange"}`), and `parseKeysetParams` (the allowlist + limit + the prefix-scoped `after` decode → 400; extra parameter names extend its allowlist). The query string itself carries no application-level length bound: the request line is capped by the server's `MaxHeaderBytes` before any handler runs — the recorded reliance (the parser bounds each parameter's value, not the raw string). Every plain collection parses through `parseKeysetParams`; search and the comments list compose `strictQueryParams`/`parseLimitParam` and decode their own sort-bound cursor (the two compositions recorded in the collections pattern doc).
- `formatAPITime` in `response.go` is the canonical millisecond RFC 3339 formatter — reuse it, don't format inline.
- Self-service session list: `sessions.go` owns GET `/api/v1/users/me/sessions` (keyset list; cursor namespace `ss1.` in `cursor.go`; `SessionsList(db, now)` takes an injectable clock for the expiry-window tests; `current` is derived by comparing each item's id with `su.SessionID` — never from a client value; a NULL label is an explicit `clientLabel: null` via a pointer) and DELETE `/api/v1/users/me/sessions/{id}` (`SessionRevoke(db, secure)`: invalid id shape 400, store error → failure audit row + 500, idempotent 204, a success audit row ONLY when a row was actually deleted — the sign-out precedent — and the cookie cleared when the revoked id IS the current session). `audit.go` owns the TWO audit emitters: `logAuditEvent` (actor-only — the content administration handlers, the session revoke path, and `Auth.logAudit`, a delegating method so its many call sites read unchanged) and `logAuditTargetEvent` (actor + target + role snapshot — the account administration, email/verification, and comment-moderation events). No handler calls `audit.Event*` directly.
- List card projection: `BlogPostItem` carries description/updatedAt/creator; the creator ref `{id, username, avatarUrl}` is the ONE `userRefDTO` type + `userRefDTOFrom` projection (`user_ref.go`; `avatarURLOrNull` lives in `media.go`) shared by both content kinds' list/detail/staff DTOs. **Uploader fallback:** the four PUBLIC content handlers resolve the `uploaderFallbackUsernameCanon` account once per request (`requireUploaderFallback` — a store failure answers the standard masked 500) and project creator/updater through `contentRefFrom` — a ref without an avatar (a guard-rejected stored value counts as absent) borrows the account's served picture, and an absent ref becomes the account as a whole; the staff DTOs keep the raw refs, account status does not suppress the fallback, and a renamed, deleted, or canon-mismatched account degrades to the pre-fallback shape.
- Media: `media.go` is the single serving + URL-construction file. The served segment must be exactly `[0-9a-f]{32}.jpg|.jpeg|.png` — malformed → 400 plain text, well-formed-but-missing → 404 (asset delivery, not problems) — and a served asset carries `Cache-Control: public, max-age=31536000, immutable` (the stored file name is content-addressed and never rewritten). The storage layout builders live in `internal/media` (single source of truth) — never rebuild the path inline here. `mediaURL` is the ONLY place API responses join `PUBLIC_BASE_URL` to a stored relative path; it DROPS the 2-hex storage subdirectory (`media/images/ab/<id>.<ext>` → `/media/images/<id>.<ext>` — the wire URL never exposes the subdirectory; the regression test `TestBlogListThumbnailURLServes` pins the emitted-URL-serves loop). Legacy absolute URLs pass through unchanged until `cmd/importmedia` rewrites them — do not add prefixing or rewriting elsewhere.
- Media upload: `media_upload.go` owns POST /api/v1/media AND the shared multipart machinery. The WHOLE multipart body is framed with `http.MaxBytesReader` (file bound + 1 MiB slack); strict parts — exactly one `file`, no other fields; the declared Content-Type is ignored (magic bytes decide). `readUploadFile` (the shared framing — returns the opened file or writes the response) and `writeProcessError` (the shared error map: size/pixel/dimension sentinels → 413 `{file, tooLarge}` via `writeViolationProblems`, undecodable → 422 `{file, invalidFormat}`, else generic 500) serve BOTH upload endpoints — a change to one endpoint's framing is a change to both. No file → 422 `{file, required}`; a multipart body over the file bound + 1 MiB framing slack → 413 `{file, tooLarge}`; anything else strict-400/500. Success: 201 + `Location` = served URL path + `{path, url}` (`path` = `media.RelativePath` output — the value the create DTO accepts; `url` via `mediaURL`). Uploads use `id.New` — never the migration's content-derived IDs. No audit event, no rate limit.
- Avatar upload: `avatar_upload.go` owns PUT /api/v1/users/me/avatar — ANY authenticated user (no role floor; the session's user id IS the row written), the same `readUploadFile`/`writeProcessError` framing as the media upload, `media.ProcessAvatar` processing, then `store.UpdateUserAvatar` (ErrNotFound → generic 401 — the deletion race), then the refreshed profile via the SHARED `userProfileDTO` (the GET and the PUT can never drift). No auth_version bump (an avatar is not a revocation event). No audit event and no rate limit — the upload rulings apply; per-request cost is bounded by the body and pixel caps while concurrency stays server-level.
- Media explicit delete: `media_delete.go` owns DELETE /api/v1/media/{file} — the same served-segment parser (`parseMediaFile`), `admin`+ (`identity.CanDeleteMedia`), existence → 404 before the reference check → 409 `writeConflict` (a file referenced by any content row or user avatar is NEVER removed) → 204 + Info log with the actor. The check-then-remove TOCTOU is documented benign (the store's disambiguation-SELECT precedent). No audit event (the event list is exhaustive — the upload ruling applies). Unlike the asset path's plain-text errors, every outcome here is a JSON problem (it lives under /api/v1).
- Blog detail: `blog_detail.go` is the detail handler. Masking: unknown id, draft, archived, and published-but-unstamped all answer the SAME 404 `/problems/not-found` — do not distinguish them. ID syntax is validated FIRST (`publicIDPattern`, RFC 3986 unreserved, 1–64 chars): invalid shape → 400, valid shape that resolves to nothing → 404 — the two outcomes stay distinct. The detail GET accepts NO query parameters (`allowNoQueryParams` — unknown/duplicate/malformed → 400). `safeDownloadLink` is the read-boundary link guard: only http(s)-with-host and magnet-with-query (`magnet:?…`) reach the JSON; malformed legacy values stay in the DB and emit null — never smuggle another scheme. Creator/updater DTOs are `{id, username, avatarUrl}` — no role on public content; `updatedAt` is always emitted (the UI decides whether to display it).
- Search: `search.go` is the handler; each item carries the merged projection — `type`, `id`, `title`, `subtitle` (the blog post's display line; empty for projects, whose hits carry the key regardless), `description`, the masked `thumbnailUrl`, and the live counts. The date-sorted cursor namespaces are `sv1.` (newest first) and `so1.` (oldest first) and the title-sorted one is `st1.` (both in the shared `cursor.go` codec; blog `v1.`, projects `pv1.`) — `parseSearchAfterParam` picks the codec from the parsed sort, so a cross-sort cursor is a 400 before the store is reached. Strict params: `q` required (trimmed 1..100 runes — empty → 422 `{q,required}`, >100 → 422 `{q,maxLength}`, sanitized-to-nothing → 422 `{q,invalidFormat}` via `search.ErrNoTokens`), `type` all|posts|projects (default all, unknown → 422 `{type,invalidValue}`), `sort` date|oldest|title (default date, unknown → 422 `{sort,invalidValue}`), `from`/`to` (optional inclusive UTC calendar days, parsed by `parseSearchDateParam` — see below), `limit`/`after` via the shared `list_params.go` helpers. `search.BuildQuery` (internal/search) turns user text into the MATCH argument — the handler passes the BUILT argument to the store; user text never reaches SQL as syntax. Cursors are only meaningful with the same q+type+sort+window (documented in OpenAPI — the tuple does not encode them; the sort is bound by the namespace). This layer mints the title cursor's key via `search.SortKey` — the store never computes it. **Date window:** `parseSearchDateParam` is deliberately strict — the value must round-trip through `2006-01-02` (the canonical-spelling check — the layout's zero-padded fields already reject `2025-1-2`, so the round-trip keeps that guarantee explicit rather than incidental), the calendar must accept the day, and the year is bounded to 1970–9999 so the millisecond value stays positive; failures are 422 `{field,invalidFormat}` and never reach the store. The inclusive end day is converted here into the next day's UTC start (exclusive bound), and an inverted window is 422 `{to,invalidValue}`. The store receives `store.SearchQuery` (match, scope, sort, `SinceMS`, `UntilMS`, limit, keyset) — no date string crosses that boundary. Both bounds are POINTERS: nil is absent, because 1970-01-01 is a legal bound whose millisecond value is 0 — a zero sentinel would silently disable the window for the epoch day.
- Current-user profile: `users.go` owns GET `/api/v1/users/me` and the `UserProfile` wire DTO (`id/username/email/role/createdAt/avatarUrl/emailVerified`). It resolves its session through `requireSession` → `store.UserByID` directly (a plain read — no service layer, same as blog/projects). Unauthenticated AND the session-outlives-user-row race both answer the generic 401 (`writeUnauthorized`) — no distinguishable outcome. `avatarUrl` is projected through `userProfileDTO` → `avatarURLOrNull` → `mediaURL` to the ABSOLUTE served URL (the stored 4-segment storage form's 2-hex subdirectory never reaches the wire); null stays null, a scheme-guard failure emits null. `userProfileDTO` is the single projection shared with the avatar upload's 200. Never log the email.
- Favorites: `favorites.go` owns the eight handlers via the `favoriteKind` bundle (`BlogFavoritesKind`/`ProjectFavoritesKind` — the store's `ContentKind` descriptor, cursor prefix, log label). Cursor namespaces `fv1.`/`fpv1.` reuse the shared codec with the favorite's `created_at_ms` in the timestamp slot. The add path validates the id shape first (400), then maps every store rejection to the masked 404; remove is 204-always; the status read is 200 `{favorited}` for published content, masked 404 otherwise. 204s go through `writeNoContent` (request ID + no-store, empty body). The add handler takes an injectable `now func() time.Time` (nil → `time.Now`) for the favorite timestamp. The list's item DTO reuses `mediaURL`/`formatAPITime` like every list and carries the blog post's `subtitle` (empty for projects — the key is required on the wire).
- Roles and capabilities: `internal/identity/role.go` owns the role constants, `RoleWeight` (the draft-visibility hierarchy — the gate is the store's `staffGateClause` in `internal/store/staff_content.go`, a strict weight comparison: published OR creator OR strictly-higher), `IsValidRole`, and the capability checks. admin+ = `CanCreateContent`, `CanDeleteContent`, `CanUploadMedia`, `CanDeleteMedia`, `CanViewStaffEmails`; moderator+ = `CanModerateContent` (staff content reads, content updates, staff comment deletion), `CanViewStaffList`, `CanViewMetrics`; super-admin = `CanViewLogs`. The pair predicates encode the peer matrices: `CanResetPassword` (super-admin any, incl. self; admin moderator/user), `CanDeleteUser` (the same matrix, written explicitly so a reset-policy change cannot move deletion), `CanChangeRole` (super-admin any transition; admin moderator ↔ user on moderator/user targets), `CanChangeUserStatus` (super-admin any, incl. self; admin moderator/user; moderator user only — the one capability below the admin floor). Handlers read the session's `Role` field and use these checks — authorization is explicit per operation, never a middleware role gate.
- Content administration: `blog_admin.go` and `project_admin.go` own the staff reads, the DTOs, and the request parsers, with the create/update/delete handlers in `blog_admin_write.go` and `project_admin_write.go`. The write DTO is `{title, subtitle?, description?, thumbnailPath, status?}` for blog, `{title, description?, thumbnailPath, status?}` + admin+-only `slug?` for project UPDATE (the create body has NO slug — an unknown key is 400; a moderator-submitted slug is 403; invalid grammar → 422 `{slug, invalidFormat}`; duplicate → 422 `{slug, alreadyTaken}` via `store.ErrSlugTaken`). A `status` outside the create vocabulary (draft|published) or the edit vocabulary (draft|published|archived) is an unknown-enum 422 `{status, invalidValue}` (the vocabulary is in `docs/patterns/go/errors.md`). `thumbnailPath` is the STORAGE-relative media reference (shape — including the 2-hex subdirectory equal to the id's first two characters — plus file existence; the staff detail returns it verbatim so the edit form round-trips it — the absolute `thumbnailUrl` cannot be converted back). Downloads: BOTH write DTOs carry the REQUIRED full-replacement `downloads` array — blog rows `{resolution, magnetUrl?, torrentUrl?}`, project rows `{name, magnetUrl?, torrentUrl?}` — validated in `downloads.go` (shared `validateDownloadRows`: 1..20 rows, label 1..100 runes, links ≤ 2000 runes AND the `safeDownloadLink` grammar → 422 `{downloads, required|maxItems}` / `{downloads[i].resolution|name|magnetUrl|torrentUrl, …}` / `{downloads[i], required}` for a link-less row); the staff DTOs return `downloads` VERBATIM (no guard — the form shows what is stored); the write body bound is `maxContentWriteBodySize` (512 KiB — the downloads array outgrew the 4 KiB auth bound). Delete floors: `CanDeleteContent` (admin+). Field bounds: title 1-200, subtitle ≤500 (blog), description ≤20k runes (mirrored in OpenAPI). ETag contract: staff detail emits `"<revision>"`; update/delete require If-Match — 428 missing (`/problems/precondition-required`), 400 malformed, 412 stale (`/problems/precondition-failed` via `store.ErrConflict`). The draft-visibility gate: the write handlers PRE-READ through the same gated staff read, so a moderator addressing an admin's draft gets the masked 404 — before any precondition check. Audit: `content_created/updated/deleted` emit a success row only after the commit; a store failure (500) emits the matching failure row. Validation rejections emit nothing. The create `Location` points at the STAFF detail path (`/api/v1/admin/<content>/<id>` — the public detail masks drafts). The project slug is generated in the create handler (`slug.GenerateBase` + `-2`, `-3`, … retry on `store.ErrSlugTaken`; empty transliteration → `p-<id>`). The slug field's admin-floor test reuses `CanCreateContent` deliberately; split a dedicated predicate if the create policy ever diverges. `writeJSONBodyError` is the shared readJSON failure mapper.
- Staff content list filters: both content lists (`BlogStaffList`, `ProjectStaffList`) accept the optional `status` and `q` parameters — the allowlist in `strictQueryParams` is what enforces that no third name slips in. `parseStaffContentFilter` (`list_params.go`) validates them for both: `status` must be in `staffContentStatuses` (draft/published/archived) else 422 `{status, invalidValue}`; `q` is trimmed and bounded at `staffContentFilterMaxLen` (the public search's 100) else 422 `{q, maxLength}`. A blank value means "no filter" (the staff user list's precedent, not a 422). The handler passes a `store.StaffContentFilter` straight through — the store splits the query into words (`search.FilterTokens`) and folds them, so `dr stone` finds `Dr. Stone` at the same word boundaries the public search uses (internal/search/AGENTS.md records the remaining differences; a query with no letters or digits is a no-op filter here, not a 422).
- Staff user list: `users_admin.go` owns GET `/api/v1/users` + the `StaffUserItem` DTO. The cursor namespace is `staffUserCursorPrefix`=`uv1.` (created_at_ms in the timestamp slot). Floor: unauthenticated → 401, `role=user` → 403, else moderator+ (`identity.CanViewStaffList`). email is a `*string` with `omitempty`: set ONLY for admin+ viewers (`identity.CanViewStaffEmails`) — a moderator's response has NO email key, never null. Filters: `role` (any accepted role) and `status` (active|suspended) — an unknown value is 422 `{role|status, invalidValue}` (never silently ignored — it would change the result set's semantics). Never log emails. **Avatar field:** `StaffUserItem` also carries `avatarUrl` (`*string`, NO `omitempty` — always on the wire, null when the account has no avatar), projected by `staffUserProjection` through `avatarURLOrNull` to the ABSOLUTE served URL (the `UserProfile` shape). It is NOT role-gated, so all five `staffUserProjection` calls (the four responses: the list plus the role-change and suspend/reactivate writes) carry it; those handlers take `publicBaseURL` (the `BlogStaffList` precedent, route wiring in `internal/routes/users.go`) — `UserDelete` answers 204 with no projection and takes none.
- Password reset: `users_admin.go` also owns POST `/api/v1/users/{id}/reset-password` (the `UserPasswordReset` handler + the one-time `resetPasswordResponse`). Flow: 401 → 400 (id shape) → load target → 404 (NOT audited) → `identity.CanResetPassword(su.Role, target.Role)` 403 (AUDITED as `password_reset` failure with actor + target + target_role) → `auth.ResetPassword` → 200 `{password}` audited as success. The temp password is generated in `internal/auth` (`ResetPassword`) — never in the handler. A store `ErrNotFound` from the write maps back to the masked 404. The plaintext is returned once, no-store.
- Role change + deletion: `users_admin.go` also owns PATCH `/api/v1/users/{id}/role` (`UserRoleChange`) and DELETE `/api/v1/users/{id}` (`UserDelete`). Shared flow: 401 → 400 (id shape) → [role change: strict `readJSON` body → 422 `{role, invalidValue}`] → load target → masked 404 (NOT audited) → floor/peer 403 (AUDITED as `role_changed`/`user_deleted` failure with actor + target + the target's CURRENT role snapshot) → store write. The 409 last-active-super-admin guard is AUDITED the same way and carries the specific problem type `/problems/auth/last-super-admin` — not `/problems/conflict`. A same-role PATCH is a 200 no-op (no version bump, no audit) and the no-op check sits AFTER `CanChangeRole`, so an unauthorized same-role attempt still answers the audited 403 (authorization precedes no-ops). The target load deliberately precedes the authorization check so every audited 403/409 carries the complete actor/target/role snapshot; the accepted tradeoff is that a below-floor authenticated caller can distinguish an existing account id (audited 403) from a missing one (masked 404) — accepted because ids are opaque and not brute-forceable, and the snapshot audit is the chosen protection. Role success returns the updated `StaffUserItem` via `staffUserProjection` (email per `CanViewStaffEmails`) and audits with targetRole = the NEW role; deletion returns 204 via `writeNoContent` and audits with the PRE-delete role snapshot. Both write paths stamp `updated_at_ms` with `time.Now.UnixMilli` (no injectable clock — no handler test asserts it). All audited FAILURE rows funnel through the shared `auditTargetFailure` helper (the password reset included); `staffUserProjection` takes the shared `staffUserFields` bundle (one struct for both row shapes: the list's `store.StaffUser` and the write handlers' `identity.User`), so the list and the write responses cannot drift and a 10-argument positional call cannot silently swap two same-typed fields; the two tiny adapters (`staffUserFieldsFromRow`/`staffUserFieldsFromUser`) are the only place the row shapes meet the projection.
- Suspend/reactivate: `users_admin_status.go` also owns POST `/api/v1/users/{id}/suspend` (`UserSuspend`) and POST `/api/v1/users/{id}/reactivate` (`UserReactivate`) — both thin constructors over the shared `userStatusChangeHandler` + `userStatusChangeKind` bundle (the favorites-kind precedent: only the target status, store write, and audit event differ). Flow mirrors the role-change/deletion shape: 401 → 400 → load target → masked 404 (NOT audited) → `identity.CanChangeUserStatus` floor/peer 403 (AUDITED via `auditTargetFailure`; moderators manage users only — the one capability below the admin floor) → store write. The target-before-floor ordering carries the same accepted 403/404 disclosure tradeoff recorded with the role-change flow. The same-status no-op (200, current projection, no bump, no audit) sits AFTER authorization — the same-status no-op precedence pin; for reactivation it is load-bearing (a bump on an already-active account would revoke live sessions). Suspend success audits `user_suspended` with the unchanged role snapshot; the guard 409 (`/problems/auth/last-super-admin`, suspend only — reactivation can never trip it) is audited the same way.
- Notifications feed: `notifications.go` owns the seven handlers. The floor is AUTHENTICATED; `notificationsScope` derives `(viewerID, weight, includeStaff)`. A non-staff viewer gets their own `user_notifications` rows minus the staff-only `draft_activity` kind; at the staff floor that kind is served only under the draft gate's CURRENT weight rule (the creator, or a viewer weight strictly above the creator's — evaluated against the live content row), so a role change can withdraw a delivered notice. Mark-read, mark-all, and every delete path apply the same below-floor exclusion to the user space. The list emits PER-KIND DTOs (`accountNotificationItemDTO` — the account item shape unchanged, targetUsername/targetRole always present, null when the account is gone — and `commentNotificationItemDTO` — the comment item field set, shared by `comment_reply`, `heart`, `comment`, AND `comment_removed`; plus `contentNotificationItemDTO` for `content_updated` AND `new_content` (comment-item shape MINUS `commentId`) AND `draftActivityNotificationItemDTO` for `draft_activity` (the content shape PLUS `draftAction`, always present on that kind)) under one `[]any` items envelope (the OpenAPI oneOf discriminator on `kind`); `notificationItemDTO` dispatches with a per-kind switch (unknown kinds fall to the account shape — the five audit events are the only other kinds that exist); `event` is superseded by `kind`. The list uses the shared strict limit/after plumbing with the `nv1.` namespace; the unread-count rejects ALL query params (`allowNoQueryParams`); mark-read validates the id shape (400) then maps every `store.ErrNotFound` — unknown OR outside-scope, in EITHER id space — to the SAME masked 404 (never distinguishing them); mark-all logs the newly-inserted count. The clock-taking writes (`/{id}/read`, `read-all`, `DELETE /{id}`, `delete-all`) take an injectable `now func time.Time` (nil → `time.Now`) for their application-clock stamps (never a schema default — [sql-mapping.md](../../docs/patterns/go/sql-mapping.md) — the AuditWriter precedent). No audit emissions: read state is not an audited operation. Every item DTO above carries `read` (the store answers it per space — the user half from `read_at_ms`, the audit half from `notification_reads`), and three handlers join the surface: `NotificationsDelete` (`DELETE /{id}` — an event row of the viewer's is deleted; a visible audit event is DISMISSED for the viewer with the ledger row intact — unknown, foreign, invisible, and already-dismissed ids are the SAME masked 404, and a repeat delete is a 404 too), `NotificationsClearRead` (`POST /clear-read` — every READ event row, idempotent 204, unread rows always survive; the count is logged like mark-all's), and `NotificationsDeleteAll` (`POST /delete-all` — one transaction: every event row of the viewer deleted and every visible audit event dismissed, idempotent 204, the count logged). The audit ledger is NEVER deleted: per-item and delete-all deletions resolve to per-viewer dismissals (`notification_reads.dismissed_at_ms`), and a dismissed entry leaves the list, the count, and the unread badge.
- Comments: `comments.go` owns the read handlers and the shared shapes, and `comments_write.go` the five write handlers, via the `commentKind` bundle (the favoriteKind precedent — the store's `ContentKind` descriptor, cursor prefix, URL segment, log label) with `BlogCommentsKind`/`ProjectCommentsKind`; the segment reads the descriptor's `kind` from `store.BlogContent.Kind` (the route table still spells its patterns literally). The list resolves the session OPTIONALLY for the viewer-aware `hearted` (never a 401); the sort is `top|newest|oldest` (default top, unknown → 422 `{sort, invalidValue}` — the staff-user-list precedent); `focus` + `after` are mutually exclusive (400); endCursors mint the hearts slot ONLY under top (a time-sort cursor with a hearted last item must round-trip). `writeCreatedWithLocation` is the bodyless 201 + Location helper (Location = the thread list `?focus=<id>` — the deep-link resource, no single-comment GET). Body contract in `validateCommentBody` (trim → CRLF/LF → required/maxLength(5000 runes)/invalidFormat(control chars, LF+TAB excepted) — format characters (bidi/zero-width) deliberately pass and render as text) with `readJSONLimit` (32 KiB). Delete authorization: author OR `identity.CanModerateContent` (the content-moderation gate); the staff-deleting-others case emits `logAuditTargetEvent(r, comment_deleted, success, actor, author, "")` (no target-role snapshot); self-deletes — staff included — emit none. The 422 reply-to-reply code is `{parentId, invalidValue}`. **Heart:** `CommentsHeart` mints the notification id on the PUT path (the reply precedent) and maps `store.ErrSelfHeart` to 422 `{commentId, invalidValue}` — self-hearts are forbidden; the DELETE path skips only the self-ban — the published-only gate applies to BOTH directions, so an unheart on unpublished content is the same masked 404 and the row plus counter freeze until re-publication. **Staff role:** `commentAuthorDTO` carries `staffRole` (pointer + `omitempty`) fed by `staffRoleOrNil` (`comments.go`) — present only for moderator+ authors, so a non-staff author's role never reaches the wire and the key is ABSENT, never `null`; `isStaff` and `staffRole` read the same store derivation and can never disagree (pinned by `TestCommentsList_StaffRoleOnWire`). **Reply window:** a top-level item carries `replyCount` + `repliesEndCursor` (both pointers + `omitempty`) and its `replies` array is the inline window (≤3). The item DTO is the `commentKind` method `itemDTO` (returning `commentDTO`) — only this layer mints cursors: when the store's `HasMoreReplies` is set it encodes `repliesEndCursor` from the WINDOW'S LAST reply under `br1.`/`pr1.`. `CommentsReplies` serves GET on `…/{commentId}/replies` — the optional-session reads chain, `parseKeysetParams` with the shared limit pair (`commentRepliesDefaultLimit` ALIASED to `commentsDefaultLimit`) and the `kind.replyPrefix` namespace, masked 404 for unknown/foreign content or a parent that is unknown/foreign/a reply. Do NOT let the client build a reply cursor — the store exposes `HasMoreReplies`, and this layer owns the encoding. **Moderation notifier:** `CommentsDelete` takes the notifier seam + a clock, mints a notification id only on the NON-self path, and fans the store's `comment_removed` event out after the commit — deliberately WITHOUT `ActorUsername` (the notice is actorless; the payload must not carry the moderator's name either). `notificationKindCommentRemoved` joins the const block, the comment-shape DTO dispatch, and the kind list (`pushKinds` — `notificationItemDTO`'s default branch is the ACCOUNT shape, so a new user_notifications kind MUST join the switch). **Rate limits:** the five write constructors take a `*middleware.RateLimiter` (required — a nil panics once a validated write reaches the check); the shared `allowUserBucket` helper applies it after the cheap path/body validation and BEFORE any store read, writing the 429 + Retry-After through `writeTooManyRequests`, which logs the exceedance ONCE with the bucket and user id. Buckets: create `comment-create` + reply `comment-reply` (one shared limiter instance and budget), edit `comment-edit`, heart `comment-heart`, delete `comment-delete` (DELETE limits before the author lookup, like the other writes). Concurrency contract: comment edits carry no ETag/If-Match (a race is last-write-wins) and create carries no Idempotency-Key (a double-submitted comment is a visible duplicate the author can delete).
- Self-service reset: `auth_password.go` also owns `HandleForgotPassword` + `HandleResetPassword`. Forgot: always `200 {}` (enumeration-safe — `writeJSON` with an empty struct); 403 already-authenticated before body parsing; identifier bound 256; the identifier rate-limit key is the whitespace/case fold (`store.NormalizeCanonWhitespace`), never logged; the 500 path audits a `password_reset_requested` failure row ONLY when the service identified the account (userID non-empty — the comment/audit scope rule). Reset: token 43-char shape check BEFORE password validation (a bad token answers the generic `/problems/auth/reset-token-invalid` via `writeResetTokenInvalid`); success is `writeNoContent` + cookie cleared only when the session belongs to the reset account; the completed event is `logAuditTargetEvent` (actor == target, role snapshot).
- Email verification + change: `auth_verify.go` owns `HandleVerifyEmail` (43-char shape check → `204` via `writeNoContent`; generic `/problems/auth/verification-token-invalid` via `writeVerificationTokenInvalid`; `email_verified` audit with actor == target) + `HandleResendVerification` (401 → verified no-op `204` → shared-bucket 429 → `204`). `auth_register.go`'s `HandleRegister` calls `SendVerificationEmail` after the commit and LOGS a failure without failing the 201. `email_change.go` owns the `EmailChange` handler (users subtree): 401 → 422 requireds → shared-bucket 429 (BEFORE the write — throttled requests change nothing) → the service swap → `email_changed` audit (failure on wrong password with the session's role snapshot; success with the refreshed row's) → post-commit sends (verification to the NEW address, notice to the PREVIOUS — both logged, never surfaced) → `200` with the refreshed `UserProfile` (the same-email no-op skips both sends and the audit). `UserProfile` + `StaffUserItem` carry `emailVerified` (the staff projection passes it for every role — it is not email-gated).
- Web push: `push.go` owns the subscription/preference endpoints (POST/GET/DELETE `/api/v1/push-subscriptions`, GET/PUT `/api/v1/notification-preferences`) plus the self-test send `POST /api/v1/push-subscriptions/test`: `PushTestSend` takes the `push.TestSender` seam (nil = delivery disabled → `delivered: 0`, never an error) and a REQUIRED user-keyed limiter (bucket `push-test`, 5/10 min — the limiter runs before the send, so a limited press never spends a message). It returns `200 {"delivered": n, "endpoints": [{"id", "service", "accepted", "status?", "removed?"}]}`: n counts endpoints that ACCEPTED the message, and `endpoints` reports one outcome per attempted row so the client can say whether THIS device was the refusal (the aggregate count alone masks a refused phone). The item carries the caller's own row id, the COARSE push-service family (`mozilla` | `fcm` | `apple` | `other`) and the transport verdict only — the endpoint URL and the key material never reach it, and `PushTestSend`'s wire test pins the exact key set. `endpoints` is an EMPTY ARRAY, never null. It rejects query parameters (`allowNoQueryParams`), writes no feed row, reads no preferences, and writes no audit row. `pushKinds` is the known-kind list ordered as the `notification_preferences` CHECK (heart, comment_reply, comment, content_updated, new_content, comment_removed, draft_activity; the `user_notifications` CHECK keeps its own order) — new kinds amend it AND BOTH migration CHECKs together (contract), and `push_kind_pin_test.go` pins the six copies (the migration CHECK, both OpenAPI enums, the feed discriminator mapping, the web union, and the service worker's branch set) so a half-added kind fails the suite; the self-test's `test` kind is deliberately NOT in it (it is not a feed kind). **The draft notice is the one ROLE-SCOPED kind:** `pushKindsFor(role)` drops it below the moderator floor for the preferences READ, and `NotificationPreferenceSet` answers the same masked 404 an unknown kind gets there — the client renders the list it is given and role-checks nothing. `roleDefaultsPushOn(role, kind)` is per KIND, not per role: the audience kinds default ON for moderator+ and OFF below, while `draft_activity` defaults OFF at EVERY role (opt-in); both this floor and the sender's post-commit default read the one model predicate, `identity.CanModerateContent`. The create body validation (`validatePushSubscriptionBody`) decodes p256dh/auth STRICTLY (65/16 bytes) and rejects non-https/userinfo/fragment endpoints; the TRIMMED endpoint is what gets stored. The preference PUT body is `*bool` — a missing `pushEnabled` is 422 `{pushEnabled, required}`, never a silent false. The two GETs enforce `allowNoQueryParams`. The comments write handlers (`comments_write.go`) take the `push.Notifier` seam (nil = disabled): the reply/heart handlers hand the store's `NotificationEvent` to it ONLY when a row actually landed (after the commit) — `ActorUsername` comes from the session (the actor IS the requester). The seam covers MULTI-recipient fan-out too: the comment-CREATE handler and the blog/project UPDATE handlers (`blog_admin_write.go`/`project_admin_write.go`) fan out event lists after commit (the 'comment' and 'content_updated' kinds), and the blog/project CREATE handlers fan out the 'new_content' broadcast — a create-as-published emits it, and the update handlers' publish transition (first publication) does the same. Every event carries `DraftAction` through to `push.Event`, so the create/update handlers' fan-out loops hand the draft notice on without a second seam — the same loop serves the broadcast and the notice.
- Follows: `follows.go` owns the bell-toggle endpoints (`GET`/`PUT`/`DELETE /api/v1/users/me/follows/blog-posts|projects/{id}`) — the favorites mirror (status `{following}`, masked 404 for unpublished content, idempotent 204s, `allowNoQueryParams` on the read). No follow LIST endpoint (out of scope — the bell reads status only).
- Staff dashboard metrics: `staff_metrics.go` owns `GET /api/v1/staff/metrics` (`StaffMetrics`). Flow: 401 → `identity.CanViewMetrics` 403 → `allowNoQueryParams` 400 (the endpoint takes NO parameters; silently ignoring one would present different data than the caller asked for) → totals → activity → 200. The floor check runs BEFORE any store call, so a below-floor request never touches the database — pinned by a test that drops a metrics table and shows the role=user request still answers 403 while a moderator's answers 500. The window is one instant per request (`time.Now() - 30×24h`, `metricsActivityWindow`) shared by the SQL boundary and the wire `since`, so the payload can never describe a different window than the one it counted. The wire keeps the schema role strings as VALUES while the JSON KEYS are camelCase (`byRole.superAdmin`) and the byRole/byStatus objects are always present — a fresh database answers zeros, never omitted fields.
- Audit browser: `staff_audit_events.go` owns `GET /api/v1/staff/audit-events` (`StaffAuditEvents`) — the deferred full-audit viewer, and the surface that CARRIES the forensic fields the notifications feed withholds (`requestId`, `remoteAddr`). Flow: 401 → `identity.CanViewLogs` 403 (the same super-admin floor as the logs viewer) → `strictQueryParams(event, limit)` → event → limit → `store.ListAuditEvents` → 200. `event` is an exact match validated against `audit.EventNames` (free text never reaches SQL; an unknown value is 422 `{event, invalidValue}`), and absent or BLANK means every kind — a client building the parameter from an unselected control gets everything rather than a violation. `limit` reuses `parseLimitParam` with the 50/200 pair (part of the tail-read exception). The envelope is `items`-only, newest first, and the NULL identity columns are OMITTED from an item (`omitempty`) instead of sent as empty strings. The floor check precedes the store call.
- Staff logs viewer: `staff_logs.go` owns `GET /api/v1/staff/logs` (`StaffLogs`). Flow: 401 → `identity.CanViewLogs` 403 (super-admin — narrower than the metrics floor) → `strictQueryParams(level, q, limit)` → level → limit → `logging.Read` → 200. `level` is a MINIMUM severity (`debug|info|warn|error`, default `warn`; anything else 422 `{level, invalidValue}`); `q` is a case-insensitive substring over the WHOLE raw line (field values included) and is bounded at 256 characters (422 `{q, maxLength}`); `limit` reuses `parseLimitParam` with the 100/1000 pair — an accepted exception to the 20/100 keyset defaults, because the sink's 20 MB ceiling bounds the read regardless. The envelope is `items`-only: this is a bounded tail read, not a keyset collection, so there is no `after`/`pageInfo`/`total` (an honest `hasMore` would need a full scan). A missing log directory is an empty list with 200, and an unparseable line is skipped — never a 500. The floor check precedes the parameter parse and the file read (pinned by a broken-sink test: role=user stays 403 while the super-admin gets the 500).
